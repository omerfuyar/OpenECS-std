## 1. Rules

- The plugins follow the rules of standard plugins (OpenECS DESIGN 20): each has one job, executors run things and loaders turn files into the executors' objects, and those objects back into files, and each is a generic building block.
- Each plugin is a folder of `plugins/`, with its manifest. `presets/` holds first-party presets.
- A plugin whose functions are of a few kinds puts each kind in a namespace (OpenECS DESIGN 9.9), so Lua reads them as `parse.json.read` and `compress.zip.list`, and editors complete them by kind.
- Plugins name their dependencies in their manifests and get their functions with `require` (OpenECS DESIGN 10.5). Their signatures name their parameters, for definition files (OpenECS DESIGN 10.10).
- Errors follow OpenECS DESIGN 1.4 and 10.8. A function that can fail outside its caller, as with files, the network, devices, the GPU, the system or memory, has `out string error` last, and fails with `ECS_Fail` or `ecs.fail`; a plugin never logs those failures itself. A wrong argument, such as a bad name, size or number, is a misuse, which the plugin checks with `ECS_Check` or `ecs.check`. A failure while drawing, which returns nothing, is logged.
- In Lua, the functions that act on one of a plugin's handles are also methods of the handle (OpenECS DESIGN 10.6): `connection:send(data)` is `net.send(connection, data)`. A method's name leaves out the type, so `image:size()` is `draw.imageSize(image)`, `watch:stop()` is `fs.unwatch(watch)` and `socket:close()` is `web.socketClose(socket)`. C calls the functions. The definition files list each type's methods.
- A plugin needs nothing but OpenECS: it links no library. Its calls to SDL and SDL_ttf are resolved against the libraries beside OpenECS (OpenECS DESIGN 17.2), and the code of any other library it uses is compiled into it. Copying a plugin's folder into another OpenECS's `plugins/` is all it takes to install it.
- The libraries are submodules in `dependencies/`, which is never edited: stb_image and stb_vorbis from stb, nanosvg, dr_libs, cgltf, cglm, glslang, SPIRV-Cross, SDL_net, libcurl, mbedTLS, nghttp2, zlib with its minizip, zstd, yyjson, tomlc17, xxHash, SQLite, PCRE2, md4c, tree-sitter with its grammars of C, Lua and JSON, and pl_mpeg. A plugin includes a library's code in one of its C files, after defining what the library asks for, such as `STB_IMAGE_IMPLEMENTATION`, so the code is compiled into the plugin and its functions stay inside it.
- A library of many C files, such as libcurl and mbedTLS, is compiled into a static archive instead, and the plugin's library takes the archive's code. Its files are compiled with hidden symbols, so its functions stay inside the plugin too. Two plugins that take one archive, as web and compress take zlib's, each get their own copy of its code, as no plugin uses another's libraries (OpenECS DESIGN 20.1).
- `dependencies/other/` holds the glue files that configure a library in place of its own configure script, as OpenECS's `dependencies/other/` does: for PCRE2, its configuration, its header and its character tables, each made from the generic file PCRE2 ships.
- Submodules are at fixed commits, as OpenECS DESIGN 17.4 says. mbedTLS is at a release tag of its long-term branch, 3.6, because its branch lacks the C files that its release makes with Python scripts. nghttp2's tags lack its version header too, so it follows its branch, and `dependencies/other/` holds that header. SQLite's own repository holds its sources without the amalgamation, its one C file, which its release makes with Tcl, so `dependencies/sqlite` is a mirror of the released amalgamations, at the commit of a release whose files are the same as the release's on sqlite.org.
- SDL_image and SDL_mixer are not used: their own submodules bring large codec libraries, and these plugins need only what the small ones read.

### 1.1 Building

- `shuild.c` is the build of this repository. It runs inside a checkout of OpenECS, in its `std/` folder. OpenECS's build compiles it with shu and shuild from OpenECS's `dependencies/` into `shuild.ignore` in this folder, and runs it with the build type and OpenECS's build folder (OpenECS DESIGN 17.7).
- It builds each plugin into `bin/plugins/` and copies the presets into `bin/presets/`.
- Its build files are kept in `.shu/` here, and copies keep their files' times, so a second build compiles only the plugins whose files changed.
- A plugin's C files compile into its native library with OpenECS's flags: its warnings, and in Debug its static analyzer and sanitizers. The plugin sees OpenECS's plugin interface in the build's `include/` folder, as any plugin does. As they ship with OpenECS, the standard plugins also reuse two of OpenECS's built dependencies, SDL3 and SDL3_ttf, from `.shu/<type>/dependencies/`, which OpenECS's build names with `-d`; no other plugin sees them (OpenECS DESIGN 17.2). Every other library comes from this repository's `dependencies/`.
- `shuild.c` names, for each plugin that compiles a library in, the folders of `dependencies/` that its C files include. They are system include folders, so the library's warnings stay out of the build's. The static analyzer skips these plugins, because it takes too much memory on the libraries in them; the warnings and sanitizers stay.
- `shuild.c` also names the files that a plugin reads from its libraries, which it copies into the plugin's folder in `bin/plugins/`, such as syntax's highlight queries (27).
- `shuild.c` also names the libraries that a plugin takes as archives. Like OpenECS's dependencies, they are compiled without the warnings, the analyzer and the sanitizers (OpenECS DESIGN 17.3), into `.shu/`. The plugin's own files keep the warnings and the sanitizers, and the analyzer too unless they include a library's code, as net's include SDL_net's. Their C files compile one by one, in parallel, with the definitions that configure them, such as libcurl's `HAVE_CONFIG_H`. Each names the folders of its interface, and shuild gives them to the plugins and libraries that link it, as system include folders. A library's own libraries stay its own: libcurl gets mbedTLS's headers by linking mbedTLS, and web, which includes mbedTLS's headers too, links mbedTLS itself.

### 1.2 Tests

- The examples of OpenECS-examples are the tests of these plugins (OpenECS DESIGN 17.5): each plugin has an example that shows it, and that example's test checks it.
- This repository's checks build OpenECS's `dev` with this repository in `std/` and the examples, and run the examples' tests. The check `Format` also checks that clang-format leaves the plugins' C files as they are.
- A test loads only the plugins its preset names (OpenECS DESIGN 17.5), so an example's preset names every plugin it uses, such as `settings` for the settings window.

### 1.3 Plugins

- A plugin keeps C allocations in SDL's allocator, and gives its libraries SDL's allocator where they take one.
- A size that data gives, such as an archive entry's size, or growth that data drives, such as unpacking or a reply that arrives, allocates with SDL's functions and fails when memory runs out, since stb_ds stops the program then.
- A C plugin keeps growing arrays in stb_ds (OpenECS DESIGN 1.7), through the glue header `dependencies/other/stb/stbSDL3.h`, which sets it to use SDL's allocator and assertions; the build gives the plugins its folder and stb's as system folders. Each plugin compiles stb_ds's code into itself, in one of its C files, after `#define STB_DS_IMPLEMENTATION`.
- A C plugin's static functions are named `<Plugin><Verb><Object>`, such as `MixerFreeEcho`. The Destroy function of a handle type is `<Type>Destroy`, after the C type of the handle, such as `DrawImageDestroy`; the plugin's own Destroy is `<Plugin>Free`. A function that makes a handle is `<Plugin>New<Type>`, or the word of its service, such as `NetConnect` or `GltfLoad`. One that finds an object, and makes it the first time, is `<Plugin>FindOrAdd<Object>` or `<Plugin>FindOrOpen<Object>`. A flag that says whether a library started is `<library>Started`. clang-tidy checks these names as `.clang-tidy` says, and clang-format formats the code as `.clang-format` says, the same as OpenECS's.
- A relative path that a plugin's function reads starts at the executable's folder; a plugin reads its own files by its folder (OpenECS DESIGN 11.3).
- Lua plugins have Lua's standard libraries (OpenECS DESIGN 9.6): `io` reads and writes files, and `os` renames and removes them and gives the time. A standard plugin does not offer what they already do; fs (10) adds what they cannot.
- An object that a plugin gives is a handle (OpenECS DESIGN 10.6): Lua's garbage collector frees it when no one uses it. A plugin whose objects hold much memory, such as images, sounds, models and grids, also has a `free` function, which frees one at once and makes its handles invalid.
- Names follow OpenECS DESIGN 9.9: a plugin declares by local names, and colours are texts in Lua and `ECSColor` in C (OpenECS DESIGN 5.2).
- A panel type's callbacks name the panel's state `state`. In Lua, it is their first parameter: `draw = function(state, surface)`. In C, the parameter is `void *data`, and the typed state made from it is `state`: `Lights *state = data;`. A callback that does not read the state keeps `void *state`.

### 1.4 How panels draw

- The standard plugins draw on the CPU, into the pixels surface of the panel that calls it (OpenECS DESIGN 5.1): 32-bit ARGB pixels with premultiplied alpha. The core then uploads the surface to a texture and shows it with SDL's GPU renderer, with the core's own interface over it (OpenECS DESIGN 5.3). gpu is the one that draws on the GPU, into GPU surfaces (15).
- draw (2) is the one plugin that writes those pixels: shapes, images and text. textgrid (4) and ui (5) draw through draw, so a font or a way of blending is in one place.
- A panel that draws with the GPU instead uses a GPU surface and the sdl plugin's device (OpenECS DESIGN 5.4); no standard plugin does yet.

## 2. draw

- The `draw` plugin is the executor of 2D drawing: it draws shapes, images and text into the pixels surface of another plugin's panel. A panel's `Draw` passes its surface handle (OpenECS DESIGN 10.6) to draw's functions.
- Positions and sizes are in layout units; draw multiplies them by the surface's scale. Colours have the type `color` (OpenECS DESIGN 10.2), and draw blends them by their alpha.
- It is a native plugin. It draws shapes with its own small rasterizer, and calls SDL3 and SDL3_ttf for images and text (OpenECS DESIGN 17.2): it wraps the surface's pixels in an SDL surface, and draws text with one SDL3_ttf surface text engine, which keeps the glyphs it has drawn.
- Lines, circles and rounded rectangles have smooth edges: each pixel at an edge gets the part of the pixel the shape covers, from its distance to the edge. Rectangles keep sharp edges on whole pixels, and triangles fill each pixel whose centre is inside them, so the triangles of a mesh meet without seams.
- `draw.clip(surface, x, y, width, height, body)` clips while `body` runs: drawing into the surface stays inside the rectangle, and inside a clip around it. The clip ends when `body` returns, also when it fails, whose error is reported (OpenECS DESIGN 10.4), so a failed draw never leaves a surface clipped. `body` takes no arguments: a plugin that clips on each draw, as ui does, passes functions it made once, which read what to draw from a stack it pushes before each clip, so a draw makes no closure.
- Its functions:

  | Function                                   | Does                                                                                                                                       |
  | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
  | `fill`, `outline`                          | Fill a rectangle, or draw its edge in a thickness.                                                                                         |
  | `move`                                     | Move the pixels of a rectangle by an offset, inside it, rounded to whole pixels; the part that nothing moves into keeps its pixels.          |
| `rounded`, `roundedOutline`                | Fill a rectangle whose corners are rounded by a radius, or draw its edge in a thickness.                                                   |
  | `line`, `circle`                           | Draw a line in a thickness, and a circle: a ring of a thickness, at least a pixel, or filled with a thickness of 0.                        |
  | `triangles`, `lines`                       | Fill triangles, or draw lines, between points: a buffer of x and y floats, and indices, three or two 32-bit numbers each, or none for points in order. |
  | `newImage`, `imageSize`, `imagePixel`, `imagePixels`, `freeImage` | Make an image of type `draw.image` from ARGB pixels, give its size, a pixel or all its pixels, and free it.          |
  | `setImagePixels`                           | Replace an image's pixels with as many others, such as a video's next frame (28). |
  | `image`                                    | Draw an image stretched to a rectangle.                                                                                                    |
  | `imageTransformed`                         | Draw an image stretched to a rectangle, turned clockwise by an angle in degrees around its centre, with each pixel's colour multiplied by a colour: white leaves it as it is, and a lower alpha fades it. Its edges are smooth. |
  | `font`                                     | Give a font of type `draw.font`: `"ui"`, the core's `ecs.font`; `"mono"`, a monospace font; or the path of a TrueType file.                |
  | `styledFont`                               | Give a font in a style: words of `bold`, `italic`, `underline` and `strike`. SDL_ttf makes the style from the font's file, so it follows any font, the user's `ecs.font` too. |
  | `text`, `measure`                          | Draw text in a font at `x, y`, the top left of its line, in a size and a colour, and give its width; or give its width and line height in layout units, measured at the scale of the surface it is drawn into, as text is drawn at its size times that scale. The width ends where the next text would start, so words measured one by one add up to their line; an italic glyph's slant reaches past it. |
  | `fontFile`                                 | Give the file a font is read from, for plugins that draw text in other ways, such as gpu (15). A setting that names another file changes it. |
  | `clip`                                     | Draw only inside a rectangle while a function runs.                                                                                        |

- `"mono"` is the setting `draw.monoFont`: a monospace TrueType file, whose relative path starts at the executable's folder. Its default is JetBrains Mono, the core's own font (OpenECS DESIGN 17.1), so `"ui"` and `"mono"` are the same font until the user chooses another for either; a terminal or a code view keeps its columns when the user gives the interface a proportional font.
- A font is opened at each size asked for, and kept; a change of `ecs.font`, which draw hears through the core's event `ecs.settingChanged`, or of `draw.monoFont` opens the fonts again.
- Their signatures are in the plugin's code and its definition files (OpenECS DESIGN 10.10).

## 3. mixer

- The `mixer` plugin is the executor of sound: it plays sounds on the computer's default output, many at once. It is a native plugin, built on SDL's audio streams.
- `mixer.newSound(channels, rate, samples)` makes a sound of type `mixer.sound` from 32-bit float samples, frame after frame. Loaders, such as audio (7), make sounds this way.
- `mixer.play(sound, volume, loop)` plays a sound and gives a voice: a number above 0 that stands for this playing of it. A volume of 1 is the sound's own. A sound can play in many voices at once. It gives 0 and why when it cannot play, such as when there is no output.
- `mixer.newStream(channels, rate)` makes a stream: a sound whose samples a plugin gives while it plays, such as a synthesizer's. `mixer.queue(stream, samples)` adds samples to its end, `mixer.queued(stream)` gives the seconds that wait to play, and `mixer.finish(stream)` tells that no more come, so its voice ends once it has played them. A voice that runs out of samples before then waits, silent, for more. A stream plays in one voice at a time, and does not loop; playing it in a second voice, or queueing to a finished stream or parts of frames, is a misuse.
- `mixer.pan(voice, pan)` moves a voice from left, -1, to right, 1: the far channel's gain falls toward 0, and at 0, the middle, both keep their whole gain. A mono sound plays in both channels, so it can be panned too.
- `mixer.stop(voice)`, `mixer.stopAll()`, `mixer.playing(voice)` and `mixer.volume(voice, volume)` act on voices, and `mixer.length(sound)` gives a sound's length in seconds. A voice that has ended is forgotten; its number is not given again.
- `mixer.filter(voice, lowpass, highpass)` filters one voice: `lowpass` cuts its sounds above a frequency in hertz, such as a sound behind a wall, and `highpass` those below one, such as a sound on a telephone. 0 turns a filter off. Each is a Butterworth biquad of the Audio EQ Cookbook, on each of the voice's channels, before SDL converts the voice to the output's rate.
- `mixer.echo(voice, delay, feedback, mix)` gives one voice an echo: what it played `delay` seconds ago, up to 2, comes back at `mix`, and each echo comes back again at `feedback` times as loud, up to 0.95. A delay or a mix of 0 takes the echo away. A voice with an echo plays on after its sound ends, until its echo is about a thousandth as loud, and 30 seconds at most; `mixer.playing` is true until then, and `mixer.stop` cuts it.
- `mixer.reverb(mix, size)` adds a reverb to everything that plays, as in a room. `mix` is how much of it is heard, from 0, none, to 1, and `size` is the room's, from 0 to 1: a larger room rings longer. It gives false and why when there is no output. It follows Freeverb: eight comb filters and four all-pass filters for each channel of the output, in SDL's post-mix callback, so it costs the same for any number of voices. As in Freeverb, samples that fade to almost nothing become 0, so a reverb that rings out over silence costs no more. A reverb turned on again starts silent, without what rang when it was turned off.
- `mixer.freeSound(sound)` frees a sound now; the voices that play it finish first, because each keeps the sound.
- `mixer.keepSound(sound)` keeps a sound alive, even when no one uses its handle, until `mixer.releaseSound(sound)`; a `releaseSound` without a `keepSound` before it is a misuse. A plugin that uses a sound after giving its handle away keeps it, as audio keeps the streams it feeds (OpenECS DESIGN 10.6).
- The output opens the first time a sound plays. Each voice is an SDL audio stream bound to it, which SDL converts to the output's format and mixes with the others; a voice gives its stream samples as the stream asks for them, and flushes the stream once it has given them all. A stream's samples wait in an SDL audio stream of their own, which the main thread fills and the voice empties.
- Tests and definitions run with SDL's dummy audio driver (OpenECS DESIGN 17.5), so they make no sound.

## 4. textgrid

- The `textgrid` plugin keeps grids of characters and draws them, with draw (2), into the pixels surface of another plugin's panel, at any font size. Terminals, consoles, logs and text editors build on it: they all place text on a grid.
- It is a native plugin. A grid is a handle of type `textgrid.grid`: `textgrid.new(columns, rows)` makes one, and `textgrid.free(grid)` or Lua's garbage collector frees it.
- A cell holds one character, a Unicode code point, its foreground and background colours, and its style. A grid starts with every cell empty: a space in the theme's text colour on its background, without a style.
- A wide character, of an East Asian script or most emoji, takes two cells, as in terminals; the right cell holds nothing. Writing over half of one empties its other half. A table of Unicode's wide ranges tells which characters are wide. Draw's default monospace font has no East Asian characters, so they show only in a font that has them, set with `draw.monoFont`.
- `textgrid.put(grid, column, row, text)` writes text from a cell to the right, and cuts it at the grid's edge. `textgrid.print(grid, text)` writes at the cursor, as a terminal does: a new line moves the cursor to the start of the next row, a full row goes on in the next one, a tab moves to the next column that is a multiple of 8, and writing past the last row moves every row up by one. A wide character that does not fit in the rest of a row goes to the next; `put` leaves it out. A grid of one column leaves wide characters out, and its cursor stays. Both leave out other control characters, such as escape; `put` leaves out new lines and tabs too.
- `textgrid.colors(grid, foreground, background)` sets the colours that later writing uses, and `textgrid.style(grid, style)` the style: the words `bold` and `underline`, or an empty text for none; another word is a misuse. The monospace font has no bold face, so bold text is drawn twice, a pixel apart. `textgrid.get(grid, column, row)` gives a cell's character and style. `textgrid.clear(grid)` empties every cell and moves the cursor to the top left. `textgrid.setCursor` and `textgrid.cursor` move the cursor and give where it is. After `print` fills a row to its end, the cursor waits for the next character, which goes on the next row; until then it shows on the row's last column, and `cursor` gives that column. `textgrid.size` gives a grid's size, and `textgrid.resize` changes it. A row that `print` filled to the edge is marked as going on in the next row, so resizing joins such rows into their lines and lays the lines out again at the new width: a line wraps instead of being cut, and the cursor keeps its place in its line. When the lines take more rows than the grid has, the first rows go, so the cursor stays. `put` never wraps, so its rows stay apart.
- `textgrid.draw(surface, grid, x, y, size, cursor)` draws a grid with its top left at `x, y`, in layout units, in draw's `"mono"` font at a size; with `cursor`, a line under the cursor's cell shows it. Cells of the same colours and style in a row are drawn as one text, and a wide character alone, over its two cells. `textgrid.cell(size, scale)` gives the size of a cell, and `textgrid.fit(width, height, size, scale)` how many columns and rows fit a rectangle, so a panel can make its grid as large as itself. Both measure at the surface's scale, as `textgrid.draw` does, so their cells are the drawn ones.

## 5. ui

- The `ui` plugin builds user interfaces from elements, lays them out, draws them with draw (2), and calls their callbacks. It is a Lua plugin, so it keeps the Lua functions it is given as callbacks. Its elements are generic, in the spirit of raygui, Unity's UI and HTML, so tools build their own views from them; it has no views of one domain.
- A panel describes its elements again each time it draws: `ui.show(panel, surface, root)` lays them out in the surface and draws them. Its `event` passes each event to `ui.event(panel, event)`, which handles the events that reach an element and gives true for them. Its `destroy` calls `ui.forget(panel)`.
- An element lives until its panel's next show, which clears it and keeps its table for new elements, as an arena is reused each frame. So a panel makes its elements again at each draw and keeps none: an element that is shown a second time is a misuse.
- `ui.show` draws only what changed since the panel's last show, while the surface keeps its pixels: it compares the draw calls of the two shows, draws again the rectangles around the calls that differ, and tells the core each rectangle (OpenECS DESIGN 5.1). When both shows made as many calls, each pair that differs gets its own rectangle, and rectangles near each other are joined, so a change at the top and one at the bottom do not draw what is between them. So a panel that ui shows draws nothing else into its surface.
- When one scroll element alone scrolled since the last show, by whole pixels, nothing drawn before it changed, and what is under it is fills of one colour and an outline around it, ui moves its pixels with `draw.move`. It then draws again only what they do not show: the strip that comes into view, what changed among its children, its outline's top and bottom, and what is drawn over it, such as its scroll bar.
- An element is a table that a function of ui makes, with the element's properties. Each function takes what the element shows first, then its props, then its children:

  | Element                               | Is                                                                                                                                                                                                                           |
  | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `column(props, children)`             | Children below each other.                                                                                                                                                                                                   |
  | `row(props, children)`                | Children beside each other. With `wrap = true`, in a column, a child that does not fit the rest of a line goes on the next line, so a row of buttons becomes a grid in a narrow panel; each line shares what it leaves among its children that grow, and lines are `gap` apart. |
  | `group(props, children)`              | Children below each other in a frame, under the `title` of its props.                                                                                                                                                        |
  | `section(title, props, children)`     | A heading of a label, as below, with an arrow over its children, which show while it is `open`, true if missing. A click on the heading, or Return or Space while it has the keys, gives the new state to `onToggle(open)`; the plugin keeps `open`, as for a tree. In a list, the heading is not an item, and the children are the list's items, so Up and Down go through every open section. |
  | `scroll(props, children)`             | Children below each other, which scroll, with a scrollbar when they do not fit. It needs an `id`.                                                                                                                            |
  | `list(props, children)`               | A scroll element whose children are items to choose. `selected` is the chosen item's number; a press on an item gives its number to `onSelect`, and a click to `onActivate`. Children with `selectable = false`, such as headings, are not items. |
  | `table(columns, rows, props)`         | Rows of cells below a header of the columns' titles; the rows scroll and the header stays. It needs an `id`. A column is `{ id, title, width }`, and a row is a table of its cells' values by column id. A column is as wide as its widest cell, unless it gives a `width`. `selected` is the chosen row's number, and `onSelect` and `onActivate` get a row's number, as for a list. A click on a title gives the column's id to `onSort`; `sort` names the column the rows are sorted by, which shows an arrow, up with `ascending = true`. The plugin sorts the rows. |
  | `tree(nodes, props)`                  | A list of nodes, each below its parent and indented by its depth. It needs an `id`. A node is `{ id, label, children }`, and one with `children`, even none, has an arrow. `open` names the open nodes by id, as `{ src = true }`, and `selected` is the chosen node's id. A click on an arrow, or Space on it (5), gives the node's id and its new state to `onToggle(id, open)`; a press beside it gives the id to `onSelect`, and a click to `onActivate`. A node's `label` is a label, as below, and its `marks` are short labels at the end of its row, each `{ id, label, on, tooltip, keys }`, such as an eye and a lock, whose `keys` its tooltip names as an element's are: one shows in the accent colour while on and dimmed while off, its icons too, and a click on it, or Space on it, gives the node's id, the mark's id and its new state to `onMark(id, mark, on)`, and does not choose the node. The plugin keeps `open`, `selected` and each mark's `on`. |
  | `graph(values, props)`                | Bars of numbers, such as times, the oldest on the left, which fill its width. A value is a number, or a list of numbers that stack, each in its colour of `colors`, `accent` if missing. `max` is the top of the scale, the highest bar's total if missing; a bar above it is cut. `lines` are lines across it at values, each `{ value, color }`. It is 80 high unless it gives a height. Lua only. |
  | `separator(props)`                    | A line across a column, or up a row; `vertical` chooses the one or the other.                                                                                                                                                                                         |
  | `text(text, props)`                   | A text, each of its lines cut with an ellipsis when it does not fit. With `wrap = true`, it breaks into lines at spaces and at its own new lines, to fit the width of its column, or its own `width`; a word wider than that breaks after its slashes, so a path breaks between its folders, and between characters if a part is still wider. A line keeps the blanks it starts with. With a `wrapMark`, such as `"↪ "`, each line after a break starts with that mark, in the text's font and the theme's `textDim`, and its words start after the mark, so the lines a long line wraps into read as its rest; a line after the text's own new line has no mark. With `maxLines`, a number, the text wraps as with `wrap = true` and shows at most that many lines; when more follow, the last one it shows ends with an ellipsis, spans too. The text may be a list of spans instead, each a text or a table of its `text` and its style: `bold`, `italic`, `mono`, `underline`, `strike`, a `color` and a `link`; or a picture a line high in place of its text: an `icon`, named as `icon` names it, in the span's colour, or an `image`'s path, which fits the square. A span may be an `icon` or `image` element too. Spans wrap together, and are cut at the edge when they do not fit. A link is underlined in the accent, and a click on it, or Return while the text has the keys, gives it to `onLink(link)`; only a text with `onLink` takes the pointer. |
  | `button(label, props)`                | A button with a label, as below. `onClick()` runs when it is clicked.                                                                                                                                                                               |

The slider shows the dragged value until the release, so a tool may take only `onSubmit`. |

With `folders`, a separator such as `"."`, the texts are paths, and the popup shows one folder at a time: its folders first, each with an arrow, then its texts by their last part. A click, Return or Right opens a folder in place, below a row that goes back to the folder above, as Left and Backspace do; the chosen one's folder opens first. A search looks in every folder and shows whole paths. |

- **Labels.** What a button, a section's heading, and a tree's node and mark show is a label: a text, or a list of spans as `text` takes, so it holds icons and images beside its words, such as `ui.button({ ui.icon("lock"), " Lock" })`. A label is one line of words and pictures, which take its colour unless a span names its own, so a tree's mark dims and lights its icons with it. It holds no other elements: a click is its element's, as a button's. Choices, a menu's entries and tooltips stay texts. In C, `UiSpan` has `icon` and `image`, and `UI_LABEL(...)` makes a list of spans that ends with an empty one, for a button's and a section's `.spans` and a tree node's and mark's `spans`, in place of their text; a button's text stays its id.

- Properties of every element: `id`, `style`, `width` and `height` (a fixed size), `grow` (a share of the room left along its parent's direction), `stretch` (whether it takes its parent's whole cross size), `padding`, `gap` and `align` (`"start"`, `"center"` or `"end"`, for containers), `background`, `hoverBackground` and `border` (colours), `color`, `size` and `font` (for text: a font name of draw), `tooltip`, a text, and `keys`, the key combination that does what the element does, such as `"Ctrl+S"`, which its tooltip names after its text, dimmed; an element with `keys` and no tooltip shows its keys alone. A column or a row with `onClick` is clicked like a button.
- A style is a table of the props of an element's look, kept in a variable so elements share it: `width`, `height`, `grow`, `stretch`, `padding`, `gap`, `align`, `background`, `hoverBackground`, `border`, `color`, `size` and `font`. An element's `style` prop takes one, and the element takes each of its props that the element does not give itself. A style's own `style` is the style it builds on. A prop that is not of the look is a misuse.
- ui keeps no styles of other plugins: a style belongs to the code that made it, as any table does, such as `local CARD = { padding = 8, border = "accent" }`, and a module shares it between plugins.
- ui has its own styles, which the first-party views (12, 13, 14, 19) and ui itself use, so views look alike. `ui.styles()` gives copies of them, so a plugin that changes one changes only its own:

  | Style     | Is                                               |
  | --------- | ------------------------------------------------ |
  | `view`    | A view's root: room around it and between its parts, on the background. |
  | `item`    | A row of a list: room around it and between its parts. |
  | `title`   | A view's title.                                  |
  | `heading` | A heading among items, in the accent.            |
  | `note`    | A note, dimmed and small.                        |
  | `bar`     | A row of tools along a panel's top, a header of the panel's own controls, on `tabRow`. |

- A tooltip shows below the pointer when the pointer rests on its element for half a second, wrapped to a width. Each move starts the half second again. It goes when the pointer leaves the element, at a press or a key, and after five seconds, since a panel hears nothing when the pointer leaves it. It is drawn inside the panel. `ui.tooltip(panel)` gives the id of the element whose tooltip shows, or nil.
- A right click is for a menu. An element with `onMenu(x, y)` gets the place of a right button's release on it, in layout units, the innermost one under the pointer. A list, a table and a tree give `onMenu(item, x, y)` the item under the pointer as their `onSelect` does, or nil beside their items; a right press on an item that is not chosen chooses it alone first, so the menu is about it. Only Lua has `onMenu`.
- Data that is dropped on a panel (OpenECS DESIGN 7.9), of a type that the panel accepts, goes to `ui.event` too. An element with `onDrop(dataType, value, x, y)` gets it, the innermost one under the pointer. A list and a table give `onDrop(item, where, dataType, value)` the item under the pointer, and `where`: `"before"` when it landed on the item's upper half, and `"after"` on its lower half. A tree gives the node's id, and `"before"` on its upper quarter, `"after"` on its lower quarter, and `"into"` between, so a tool moves a node before, after or into another. Beside the items, both are nil. Only Lua has `onDrop`.
- A list, a table and a tree drag their items. A press on an item and a move of `ecs.dragThreshold` layout units give the item, or the node's id, to `onDrag(item)`, which gives a type and a value. ui starts the core's drag of them (OpenECS DESIGN 7.9), or none when it gives nil. So a tool drags a node that is chosen already, which a press does not give to `onSelect` again. Only Lua has `onDrag`.
- `ui.menu(panel, x, y, entries)` opens a menu in a popup (OpenECS DESIGN 4.6) at a point of the panel, in layout units, such as where a right click was. An entry is `{ label, keys, enabled, onClick }`, `{ label, entries }` is a submenu, and `{ line = true }` is a line between entries. `keys` is shown at the entry's right, to say which keys do the same; the plugin that binds them binds them itself. An entry with `enabled = false` is dimmed and does nothing. A click on an entry, or Return, closes the menu and runs `onClick()`; Up and Down move between the entries that are enabled, round from the last to the first and back, and Escape or a press outside closes it. A submenu has an arrow at its right; a click, Return or Right opens its entries in place of the menu's, in the same popup, below a row that goes back, as Left and Backspace do. It opens in place, and not beside the menu, as a popup is anchored to its panel only (OpenECS DESIGN 4.6).
- An element without an `id` gets one from its parent's id and its place, so it keeps its state from one draw to the next as long as the tree keeps its shape. In C, a button's id is its label unless its props give one, so two buttons with one label need ids.
- Layout: each element gets the size it needs; then the room left along a container is shared by the children that grow, by their shares. Containers, separators, a list's items, and fields, key elements, sliders, selectors and dropdowns in a column, stretch across their parent; other elements keep their size, aligned by the parent's `align`, but no larger across than the parent's room unless they give a fixed `width` or `height`, so a text that does not fit is cut with an ellipsis rather than drawn over its neighbours.
- A click is a press and a release of the left button on the same element. The element under the pointer shows it. The wheel scrolls the scroll element under the pointer, and the scrollbar's thumb can be dragged; a press beside the thumb moves it there.
- A field or key element that has the keys takes text input (OpenECS DESIGN 4.6): text goes in at the field's cursor, which Left, Right, Home and End move, and Ctrl with Left and Right moves by words; Backspace and Delete take the character before and after it, or the word with Ctrl; Return submits the field, and Escape, or a click elsewhere, drops what was typed. A field selects text too: a move with Shift selects from the cursor, Ctrl+A selects all of it, and a drag selects what it passes over. A press puts the cursor at the pressed character, and with Shift selects up to there. Typing, Backspace and Delete replace the selection. Ctrl+C copies it to the clipboard, Ctrl+X cuts it, and Ctrl+V pastes text in its place, with its lines joined by spaces, as a field holds one line.
- `ui.matches(query, text)` tells whether a text holds each word of a query, the parts between its blanks, whatever their case. An empty query matches every text. A view that searches several texts of an item, such as a name and a description, joins them with new lines. Ctrl+F gives the keys to the panel's first search, and Escape in a search that holds text clears it, before a second Escape takes the keys away.
- `ui.edit(panel, id)` gives a field, a key element or a list the keys, as a click does. Given an id that the last layout does not have, such as before the panel's first show, or of a field that shows from the next draw, it gives them at the next show, if that layout has it. And `ui.focus(panel)` gives the id of the field or key element that takes typing, or nil.
- Tab gives the keys to the next element that takes the pointer, in the order of the tree, and Shift+Tab to the one before; they go round at the ends, and scroll the element into view. That element shows a ring. Return or Space presses it as a click does, Left and Right change a selector or a slider, and Escape takes the keys away. A scroll element with more than it shows is a stop, so the keys scroll it. A field or key element that gets the keys takes typing at once, and Tab leaves it. A press gives the pressed element the keys, without a ring, so Tab goes on from it; a press on a list's item gives the list the keys. Keys that a plugin binds for its panel type (OpenECS DESIGN 7.8) reach the plugin first.
- An element made of parts is one stop, and Left and Right go through its parts. A text is one stop, with the ring on its first link; Left and Right move the ring along its links, and Return or Space gives that link. A list is one stop with its items and what is in them. Up and Down choose an item, and the ring shows on it. Left and Right go through the interactive elements in the chosen item, its parts, such as a tree node's arrow and marks, and back to the item itself; the ring shows on the part, and stays at the same place in the row as Up and Down choose another item. Space presses the part, and does nothing on the item itself. Return gives the item to `onActivate`, wherever the ring is.
- A list, a table and a tree may have many chosen items: `selected` is then a list of numbers, or of a tree's ids, and each is highlighted; Up, Down and Return act from the first. A press gives `onSelect` how it chose, as its second argument: `"toggle"` with Ctrl, to add the item to the chosen ones or take it out, and `"range"` with Shift, with a third argument, the items from the first chosen one to the pressed one, in the order shown. A plain press gives neither, and chooses the item alone. The plugin keeps what is chosen, as it keeps `selected`.
- A list handles Up, Down and Return itself, as a selector handles Left and Right. The list that has the keys, or holds the element that has them, chooses the item above or below with Up and Down, gives it to `onSelect`, and scrolls it into view. Return gives the chosen item to `onActivate`, or clicks the item when the list has none, unless an element in the list has the keys, which Return presses. A panel whose list takes these keys from the start gives it the keys with `ui.edit`. A tree and a table are lists too.
- A long list builds only the items in view. `ui.range(panel, id, count)` gives the first and last items to build, those in view and half a view around them, and the list gets `count`, its number of items, and `first`, the number of its first child: `ui.list({ id = "entries", count = #entries, first = first }, items)`. The items not built take the height each had when it was last shown, or the average of those shown, so the scroll bar stays in place. Up, Down, Return and `onSelect` reach an item that is not built, and `ui.revealItem(panel, id, index)` scrolls to one by its number. A panel that is not shown yet builds every item once. In C, `UiProps` has `count` and `first`, and `ui.functions.range` gives the range. A tree needs none of this: it is given every node, and builds only the rows of the shown nodes in view and near it, which it learns when its panel shows, in Lua and in C alike; `ui.reveal` scrolls to a node that is not built.
- The scroll element that has the keys, or holds the element that has them, scrolls with the keys: Up and Down by a line, unless it is a list, Page Up and Page Down by a page less a line, and Home and End to its ends.
- A row whose children need more than its width shares the width that the others leave among its wrapped texts and its columns, so their text breaks into more lines.
- ui keeps the images it read, by path and scale. When it holds 64, it drops those that the last two shows did not use. A file that could not be read is tried again after two seconds.
- `ui.rect(panel, id)` gives an element's rectangle in the last layout, as a table of `x`, `y`, `width` and `height` in layout units, or nil when no element has the id, and `ui.reveal(panel, scroll, child)` scrolls a scroll element so a child shows, or a tree so the node of that id shows.
- A list of children may hold `false`, which is left out, so a child is shown on a condition with `shown and ui.text(...)`. A `nil` ends the list, as in any Lua list.
- Ids. An element that keeps something between draws needs an `id` of its own, and its function raises an error without one: a scroll, list, table and tree keep their offset, and a field, number and key what is typed. Any other element gets an id from its place among its parent's children, which a child that is left out does not change. An id that two elements of a panel have is a misuse, and so is a prop that ui does not know.
- `ui.inspect()` turns the inspector on or off, for the person who builds a panel; a key or the launcher calls it. It outlines every element of every panel that ui shows, and names the one under the pointer: its type, id, place and size in layout units, and the layout props it has. `ui.inspected(panel)` gives that element to code.
- **C.** C gives ui no functions, so a plugin in C describes its elements, and ui builds them with the same element functions:
  - `ui.showDescription(panel, surface, description)` builds the elements of a description and shows them. A description is a table: `type`, the element function's name, such as `"button"`; `props`, without callbacks; `value`, the first argument, such as a text or a state; `choices`, `columns`, `rows`, or `nodes` with a tree's `open` and `selected`; and `children`.
  - A described element with an id keeps what each of its callbacks gets, such as `onClick` or `onChange`. `ui.take(panel, id, callback)` takes it, as a table of `value` and, for `onToggle`, `open`, or, for `onMark`, `mark` and `on`, or gives nil if the callback did not run. A described text with a link keeps its `onLink` too, under the id `""` when it has none, so a panel takes the links of every text of a description, such as markdown's (26). What no one took is forgotten at the next `showDescription`, so each draw takes only what happened since the last. A column or row with `clickable = true` is clicked like a button.
  - A description with a prop that ui does not know is a misuse, so `ui.h` and ui cannot name a prop differently unseen.
  - ui's `header.h` ends `ui.h` (OpenECS DESIGN 10.10). Its macros describe the elements in an immediate style, in the manner of Clay's `CLAY`: `UI_SHOW(&ui, panel, surface) { UI_COLUMN(.padding = 8) { ... } }`. A container's block holds its children, and the props are designated initializers of `UiProps`.
  - The macros cover every element of Lua's ui, with the same props, so a plugin in C builds the same interface as one in Lua. They take what changed before they describe an element: `UI_BUTTON` gives whether the button was clicked, and `UI_TOGGLE(&on)`, `UI_SLIDER(&value)`, `UI_NUMBER(&value)`, `UI_SELECTOR`, `UI_TABS` and `UI_DROPDOWN(&selected, choices)`, `UI_FIELD`, `UI_PATH` and `UI_KEY(buffer, capacity)`, `UI_LIST(&selected)`, `UI_SECTION(&open, title)`, `UI_COLOR(buffer, capacity)`, `UI_SEARCH(buffer, capacity)`, `UI_TABLE(&selected, columns, cells, rowCount)` and `UI_TREE(&selected, nodes)` write the new state into the plugin's variables. A table's columns are `UiColumn`s, and its cells texts, row after row; `UI_SORTED(id)` gives the column whose title was clicked. A tree's nodes are `UiTreeNode`s, whose `open` bools `UI_TREE` writes, and a node's `marks` are `UiTreeMark`s, whose `on` bools it writes too. `UI_ACTIVATED(id)` gives the item of a list that was activated, and `UI_CLICKED(id)` whether a clickable column or row was clicked. `UI_SPANS(spans, count)` describes a text of `UiSpan`s, and gives the link that a click on one gave, or nullptr. A button's label is its id if it has none. `UI_SEARCH` gives whether the query changed, and `Ui_Matches(query, text)` is `ui.matches`.
  - In `UiProps`, a number left 0, a flag left unset or a text left nullptr is left to ui. A number is `UI_ZERO` for 0, and a flag is `true` or `UI_FALSE`. `grow = UI_FIXED` keeps an element from growing, and `min` and `max` count when they differ. The props have Lua's names. A list, table or tree in C chooses one item, as its `selected` is one number, or a tree's one id; Ctrl and Shift choose as a plain press does.
  - A described list, table or tree keeps `onActivate`, and a table `onSort`, only when its props ask with `onActivate = true` or `onSort = true`, since a list with `onActivate` behaves differently (see above); `UI_ACTIVATED(id)` gives the activated item's or row's number, `UI_ACTIVATED_NODE(id, nodes)` a tree's node's id, and `UI_SORTED(id)` the column. A described field with `valid = UI_FALSE` keeps Return from giving its text, as an `onSubmit` that gives false does. `UI_SUBMITTED(id)` says whether Return was pressed in a number field.
  - A style in C is a `UiProps` that holds only look props, often a `static const` one, and `.style` points to it. `Ui_Init` copies ui's own styles into the `Ui`, as `ui.styles.note` and the others.
  - `Ui_Init(&ui, plugin)` looks up ui's functions, from the plugin's `Init`, and `Ui_Event(&ui, panel, event)` gives a panel's event to ui. c3_ui shows the same controls in Lua and in C (OpenECS-examples).
- Positions are in layout units, and colours are the theme's unless an element names others, each in its job (OpenECS DESIGN 12.4). ui fills the surface with `panel` first. Buttons, selectors, dropdowns and the colour's swatch are `button`, `buttonHover` under the pointer and `accent` while pressed or chosen. Fields, number fields, key elements, check boxes, and the tracks of sliders are `field`, with a line of `frame`, or of `accent` while the field has the keys. A chosen item is `selected`, and an item under the pointer `hover`. A table's header, a tab's line and a `bar` are `tabRow`. Separators and the lines of groups, lists, tables and trees show the parts apart. A scroll bar has no track: its thumb is a pill in the bar's width, `button`, `buttonHover` under the pointer and `accent` while it is dragged.
- Its sizes are its settings, in layout units, so the user can change them: `ui.paddingX`, `ui.paddingY`, `ui.checkSize`, `ui.fieldWidth`, `ui.scrollbarWidth`, `ui.thumbMin`, `ui.wheelStep` and `ui.radius`.
- Controls have rounded corners of `ui.radius`, 3 by default, as the core's menus and groups do (OpenECS DESIGN 6.9): buttons, fields, check boxes, dropdowns, selectors, colour swatches and tooltips; popups and their highlighted rows too, with one unit more for popups. So do the backgrounds and borders of other elements, such as a chosen item, an item under the pointer and a group's frame, and the ring of the element that has the keys. An element as wide as its surface, such as a `bar` or a view's root, stays square, as it meets the panel's edges. A switch is a pill, and 0 makes every corner square.

## 6. image

- The `image` plugin is a loader: it reads image files into images of draw (2), which draws them, and writes those images to files. It is a native plugin.
- stb_image reads PNG, JPG, GIF, BMP, TGA, PSD, HDR and PNM files; nanosvg reads SVG files. `image.load` gives a GIF's first frame.
- `image.load(path, scale)` reads a file's bytes and reads them as `image.decode` does, into a new image of type `draw.image`, at a scale of its own size: a raster file is stretched, and an SVG file, whose size is its own at 96 dots per inch, is drawn at that scale, so it stays sharp. A file that cannot be read gives nil and why.
- Each call reads the file again; a plugin that draws an image many times keeps it.
- `image.decode(bytes, scale)` reads an image from the bytes of its file, such as a PNG file's held in a model (8), at a scale as `load` does. Bytes that start with `<` are read as SVG. Bytes that are not an image are reported and give nil.
- `image.loadFrames(path, scale)` reads the frames of an animated GIF file, each into a new image, at a scale as `load` does. It gives a list of frames, each a table of its `image` and the `seconds` it shows for. Another image file gives one frame of 0 seconds. A plugin shows the frames one after another with a timer; image only reads them.
- stb_image reads out of its buffer for a GIF frame that restores the frame before it. So image changes that disposal, in its copy of the file, to restoring the background. stb restores the background as it was before the frame, so the frames look the same.
- `image.save(image, path)` writes an image of draw to a file, in the format its extension names: `.png`, `.jpg` or `.jpeg`, `.bmp` or `.tga`. stb_image_write writes them; a JPG file is written at a quality of 90 in 100. A relative path starts at the executable's folder. It gives false and why when the file cannot be written.
- `draw.imagePixels(image)` gives the pixels that `image.save` writes. In C they stay the image's, so a plugin reads them only while the image lives.

## 7. audio

- The `audio` plugin is a loader: it reads sound files into sounds of mixer (3), which plays them. It is a native plugin.
- dr_wav, dr_mp3 and dr_flac from dr_libs read WAV, MP3 and FLAC files, and stb_vorbis reads Ogg Vorbis files. A file is read a piece at a time into 32-bit float samples: to its end into a sound, or while a stream plays.
- `audio.load(path)` reads a file into a new sound of type `mixer.sound`. A file that cannot be read gives nil and why. Each call reads the file again.
- `audio.stream(path)` opens a long file, such as music, and gives a stream of mixer (3) that it feeds while it plays: a timer keeps half a second of the file waiting in the stream, read a quarter of a second at a time. At the file's end, audio finishes the stream, so its voice ends once it has played. audio keeps the stream until then, so a stream plays to its end even when no one uses its handle. A stream that never plays keeps its file open until audio quits.

## 8. gltf

- The `gltf` plugin is a loader: it reads glTF 2.0 models with cgltf, `.gltf` files with the files they name, and `.glb` files. It is a native plugin, and does its matrix and quaternion math with cglm (16). It gives a model's parts and their data as buffers that draw's `triangles` and `lines` (2) take, or that a GPU plugin uploads.
- `gltf.load(path)` reads a model and gives a handle of type `gltf.model`, which owns all of it, and `gltf.free(model)` frees it now. Each call reads the file again. A file that cannot be read, or that is not valid glTF, gives nil and why. A mesh, primitive or image number that the model does not have is a misuse.
- `gltf.describe(model)` gives a table of the model's parts. Meshes, materials and nodes are lists, and they name each other by their numbers in those lists, from 1:

  | Field       | Holds                                                                                                                                                                                                                                                                                         |
  | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `meshes`    | Each mesh's `name` and `primitives`. A primitive has a `mode` (`"triangles"`, `"triangleStrip"`, `"triangleFan"`, `"points"`, `"lines"`, `"lineLoop"` or `"lineStrip"`), a `material`, the names of its vertex `attributes`, such as `POSITION`, and its numbers of `vertices` and `indices`. |
  | `materials` | Each material's `name`, its base `color`, as four numbers from 0 to 1, its `texture`, the base colour's image file, when it is a file, and its `image`, the number of the base colour's image in `images`.                                                                                     |
  | `images`    | Each image's `name`, its `mimeType`, such as `"image/png"`, when the model gives one, and its `file`, when it is a file. An image inside the model, as in a `.glb`, has no file.                                                                                                                |
  | `nodes`     | Each node's `name`, its `mesh`, its `children`, and its `matrix`: 16 numbers, column by column, that place it in its parent.                                                                                                                                                                  |
  | `animations` | Each animation's `name`, and its `duration` in seconds: the time of its last key.                                                                                                                                                                                                             |
  | `skins`     | Each skin's `name`, and its `joints`: the nodes whose moves bend the meshes it skins. A node with a skinned mesh names its `skin`.                                                                                                                                                            |
  | `roots`     | The nodes that the model's scene starts from.                                                                                                                                                                                                                                                 |

- `gltf.attribute(model, mesh, primitive, name)` gives a vertex attribute of a primitive as 32-bit floats, one after another for each vertex: three for a `POSITION`, two for a `TEXCOORD_0`. Whole numbers and sparse data are converted. `gltf.indices(model, mesh, primitive)` gives its indices as 32-bit whole numbers, from 0; a primitive without indices gives its vertices in order. Both give an empty buffer for a missing mesh, primitive or attribute, and their buffer is kept until the next call of `attribute`, `indices`, `image`, `pose` or `skin` on the model.
- `gltf.pose(model, animation, seconds)` gives each node's matrix in its parent at a time of an animation, 16 floats a node, in the order of `nodes`, as `matrix` is. Animation 0 gives the nodes' own matrices. Before an animation's first key a node takes the first key's value, and after the last the last's. Steps, linear keys, with rotations turned along the shorter way, and cubic splines are read as glTF says; morph weights are left out. A plugin loops an animation by giving the time modulo its `duration`.
- `gltf.skin(model, mesh, primitive, skin, animation, seconds)` gives a primitive's positions where a skin's joints move them at a time of an animation, three floats each, in the model's space, as glTF skins them: each vertex goes through the joints that its `JOINTS_0` names, by the shares that its `WEIGHTS_0` gives, after the inverse of where the joint was when the mesh was bound. A primitive without them, or a missing skin, gives its positions as they are. A joint past the skin's inverse bind matrices keeps the identity. The skinning runs on the CPU.
- `gltf.image(model, image)` gives the bytes of an image, such as a PNG file's, from its own file next to the model, or from inside the model. `image.decode` (6) makes a draw image of them. A missing image gives an empty buffer, and the buffer is kept until the next call of `attribute`, `indices`, `image`, `pose` or `skin` on the model.
- In Lua a buffer is a string, which `string.unpack` reads, such as `string.unpack("<fff", positions)` for the first position.

## 9. net

- The `net` plugin makes TCP connections and servers, TLS connections and servers, and UDP sockets, with SDL_net, which is compiled into it. It is a native plugin. Nothing it does blocks the program: a plugin asks for the state of a connection, and takes what arrived, when it wants, such as from a timer.
- **TCP.** `net.connect(host, port)` starts a connection and gives a handle of type `net.connection`. The host's name resolves in the background. `net.status(connection)` gives 1 once it is connected, 0 while it waits, and -1 if it failed or closed; `net.error(connection)` then gives why. A port outside 1 to 65535 is a misuse.
- `net.send(connection, data)` queues data to go out, and gives false and why if the connection is not connected yet, failed or closed. `net.receive(connection, most)` takes what has arrived, at most a number of bytes above 0, and gives an empty buffer if nothing has. The buffer is kept until the next receive on the connection. A connection that the other side closed fails.
- `net.listen(host, port)` waits for connections on a port of one address of this computer, such as `127.0.0.1`, which only this computer's programs reach, or of every address for an empty host, and gives a handle of type `net.server`, or nil and why if it cannot. Port 0 picks a free port, and `net.port(server)` tells which: SDL_net does not tell the port that the system chose, so net tries ports from 49152 to 65535 at random, 64 at most, and lets no other socket share the one it takes. `net.accept(server)` gives a connection that a client made, or nil.
- **TLS.** `net.connectTLS(host, port)` starts a TLS connection, with mbedTLS, which is compiled into it too (1). Its status is 0 until the TLS handshake is done, and -1 if it fails, such as when the server's certificate is not trusted or not for the host. It checks the certificate against the system's trusted certificates, as web does (11). Then `send` and `receive` move the data in and out of TLS.
- `net.listenTLS(host, port, certificate, key)` waits for TLS connections, on an address as `listen` does, with a certificate and its private key from PEM files, whose relative paths start at the executable's folder. It gives nil and why if it cannot listen or cannot read them. The connections it accepts do their handshake as a client's do, and their status is 1 once it is done. A connection keeps its server's configuration, so it works on after the server's handle is gone.
- `net.trust(path)` adds the certificates of a PEM file to the trusted ones, for the TLS connections that do their handshake later, such as a test server's own certificate. It gives false and why if the file cannot be read.
- `net.close(connection)` closes a connection. Lua's garbage collector, or the plugin that made it, frees a connection or a server, and closes it.
- **UDP.** `net.udp(port)` opens a socket of type `net.udp` on a port of every address of this computer; port 0 picks a free one. Datagrams may be lost or come in another order, and nothing tells.
- `net.sendTo(socket, host, port, data)` sends a datagram. The host's name resolves in the background: the datagram waits, behind the ones sent before it, and leaves once the name resolves. A socket keeps the last 8 hosts it resolved, so sending to them again does not resolve them again.
- `net.receiveFrom(socket)` takes a datagram that has arrived, with the address and port it came from, and gives an empty buffer if none has. The buffer and the address are kept until the next `receiveFrom` on the socket.
- For every address, SDL_net listens on every family of addresses at once, and fails if one is missing; then IPv4 alone is tried, for servers and UDP sockets.

## 10. fs

- The `fs` plugin does with files and folders what Lua's `io` and `os` cannot: it lists folders, tells what a path is, makes and removes folders, copies files and watches folders. It is a native plugin, built on SDL's filesystem functions and the system's own watching, so it needs no library. Moving is `os.rename`. `os.remove` cannot remove a folder on Windows, so plugins remove with `fs.remove`.
- `fs.info(path)` gives a table of what a path is: its `type`, `"file"`, `"folder"` or `"other"`, its `size` in bytes, and `modified`, when it last changed, in seconds since 1970. A path that does not exist gives nil.
- `fs.list(folder, pattern)` gives the entries of a folder whose names match a pattern, sorted by name: each a table of its `name` and the fields of `fs.info`. In a pattern, `*` stands for any characters but `/`, and `?` for one; an empty pattern matches every name. The entries of the folder's folders are not listed. A folder that cannot be read gives nil and why.
- `fs.makeFolder(path)` makes a folder, and the folders above it that are missing. `fs.remove(path)` removes a file, or a folder that is empty. `fs.copy(from, to)` copies a file, replacing what is at the new path. Each gives false and why when it fails.
- `fs.watch(folder, changed)` watches a folder and gives a handle of type `fs.watch`. When an entry of the folder is added, removed or changed, `changed` gets the folder, ending with `/`, the entry's name, and `"added"`, `"removed"` or `"changed"`. A rename is the old name removed and the new one added. The entries of the folder's folders are not watched. Changes are read ten times a second, up to 8 reads of them each time, so one write may come as several changes, and a busy folder never holds the program. `fs.unwatch(watch)` stops a watch now; a watch also stops when no one uses its handle. A folder that cannot be watched, or a file, gives nil and why.
- A watch that loses changes, when they come faster than they are read, gets `"overflow"` with an empty name, so its owner reads the folder again. A watch whose folder is removed, or can no longer be watched, gets `"gone"` with an empty name, once. Both are reported too.
- Watching uses inotify on Linux and `ReadDirectoryChangesW` on Windows, as SDL has no way to watch. On other systems, such as macOS, fs reads each watched folder again every half second, and tells what was added, removed, or changed in size or time.
- `fs.folder(name)` gives a folder of the computer, ending with `/`: `executable`, the executable's folder, or one of the user's folders, `home`, `desktop`, `documents`, `downloads`, `music`, `pictures`, `videos`, `screenshots` or `templates`. A folder the system does not have gives nil.
- Reading and writing what files hold is Lua's `io` in Lua, and SDL's `SDL_LoadFile` and `SDL_SaveFile` in C.

## 11. web

- The `web` plugin makes HTTP and HTTPS requests, and WebSocket connections. It is a native plugin: libcurl makes them, with TLS from mbedTLS, HTTP/2 from nghttp2, and compressed answers from zlib and zstd, and all are compiled into it (1). libcurl is built for HTTP, HTTPS and WebSockets only, and resolves names on a thread of its own.
- HTTPS uses HTTP/2 when the server offers it, and HTTP/1.1 otherwise; plain HTTP and WebSockets use HTTP/1.1. A request asks for a compressed answer, with gzip, deflate or zstd, and `web.body` gives it uncompressed; `web.header(request, "Content-Encoding")` still names how it came.
- Nothing it does blocks the program: one thread of the plugin runs every request, many at once.
- `web.get(url, done)` starts a GET request and gives a handle of type `web.request`. `web.request(method, url, headers, body, done)` starts a request with any method, such as `"POST"`; the headers are a list of texts, such as `{ "Content-Type: application/json" }`, and a body that is not empty is sent. A request that cannot be made gives nil and why; one to a URL that is not HTTP or HTTPS fails, as one to a host that cannot be reached does.
- `done`, if given, is a kept callback (OpenECS DESIGN 10.4): web calls it on the main thread with the request once it is done, and then releases it. The request goes on when its handle is dropped, and `done` gets it in a new handle. Without `done`, a plugin asks for the request's state when it wants, such as from a timer, as with net (9).
- `web.status(request)` gives 0 while the request runs, the answer's HTTP status once it is done, such as 200 or 404, and -1 if it failed, such as when the host cannot be reached or its certificate is not trusted. `web.error(request)` gives why it failed.
- Once it is done, `web.body(request)` gives the answer's body as a buffer, a string in Lua, and `web.header(request, name)` one of its headers, or nothing. A request follows up to 10 redirects, and these are the last answer's.
- `web.free(request)` frees a request now, and stops one that runs; its `done` is not called. Lua's garbage collector, or the plugin that made it, frees it otherwise.
- The setting `web.timeout` is the number of seconds a request may take before it fails; 0 means no limit. For a WebSocket connection, it limits only how long connecting takes.
- **WebSockets.** `web.socket(url, headers)` starts a connection to a `ws://` or `wss://` URL and gives a handle of type `web.socket`. As with net (9), nothing blocks: a plugin asks for the connection's state, and takes its messages, when it wants, such as from a timer. In Lua, the socket's methods do the rest; in C they are `socketStatus`, `socketError`, `socketSend`, `socketReceive` and `socketClose`.
- `socket:status()` gives 1 once the server took the connection, 0 while it connects, and -1 if it failed or closed. `socket:error()` gives why.
- `socket:send(data, text)` queues a message, as text or as bytes, and gives false and why if the connection failed or closed. A message sent while the connection connects waits, and goes once it is open. Each message goes in one frame.
- `socket:receive()` takes the oldest message that arrived, a buffer, and its type, `"text"` or `"binary"`. It gives nothing as the type if no message waits. A message that the server sent in many frames comes as one. The buffer is kept until the next receive on the connection.
- libcurl answers the server's pings. A close from the server, or the end of its connection, closes the connection.
- `socket:close()` closes a connection and frees it now. Lua's garbage collector, or the plugin that made it, frees it otherwise.
- HTTPS checks a server's certificate against the system's trusted certificates: the file that `SSL_CERT_FILE` names, or the one where Debian, Ubuntu, Arch, Fedora, openSUSE or Alpine keep it. Windows has no such file, so there they come from its store of trusted root certificates, which crypt32 reads; net reads them the same way. The proxies that `http_proxy`, `https_proxy` and `no_proxy` name are used.
- The plugin gives libcurl and mbedTLS SDL's allocator.

## 12. The settings window

- The first-party Lua plugin `settings` is built with ui (5). The core's settings file loads it in every tool (OpenECS DESIGN 12.3). It binds `,` after the prefix to `settings.open` (OpenECS DESIGN 7.8), and adds it to the title bar's menu Tools (OpenECS DESIGN 6.8); `settings.open` opens the window as a panel of type `settings.window`, or shows the one that is open.
- The window lists every declared setting under a title for its owner: the core's first, then each plugin's, each by name. A row shows the setting's name and description on its left, and a control with its value in effect on its right. The two sides share the row's width, so the controls line up and grow with the window, and the description wraps within its side, so it never runs under the control.
- The control depends on the type: a switch for a `bool`, a dropdown for a `choice`, a key element for a `key`, a colour element (5) beside a field for a `color`, whose picker has alpha when the value has, a path element (5), whose button opens the file dialog, for a `path`, and a field for the other types.
- A setting that the user's settings file sets shows its name in the accent, and a Reset button beside its control, whose tooltip shows the value below the user's. The button sets the setting to nil (OpenECS DESIGN 12.2), so the preset's, the theme's or the default value applies again. A `list` or a `table` shows as a Lua table, such as `{ 1, 2 }`.
- A field's text must read as a value of its setting's type, and shows as wrong while it does not: a number, a colour such as `#18191C`, or, for a `list` or a `table`, a Lua table, which is read with no access to anything. Return saves a text that can be read; a text that cannot is reported, and typing goes on.
- The window changes values in the user's settings file (OpenECS DESIGN 12.2): a step back or forward toggles a `bool`, cycles a `choice`, and adds or takes 1 from an `integer` or a `number`.
- Up and Down choose a setting, as the list handles them (5). Return, when no element of the window takes it, toggles a `bool`, cycles a `choice`, and gives the other controls the keys. The functions `settings.previous` and `settings.next` change the chosen setting a step back or forward; the plugin binds them for its panel type (OpenECS DESIGN 7.8) to Left and Right. While a field has the keys, they leave it alone.
- The settings are a ui list (5), in a section for each owner, under the window's title; a click on a section's heading closes or opens it, and Up and Down go through the settings of the open sections. Choosing a setting with the keys scrolls it into view, and a press chooses the setting under it, while its control gets the press too.
- A search (5) under the title shows only the settings whose name, description, owner or value matches it, with their sections open; Up and Down choose among them while it has the keys.
- The window reads the settings again on `ecs.settingChanged` and `ecs.pluginsChanged`, so a value that another plugin sets, and the settings of a plugin that is enabled, show at once.
- The panel's saved state is the chosen setting and the owners whose sections are closed.

## 15. gpu

- The `gpu` plugin draws into the GPU surface of another plugin's panel, on the GPU (OpenECS DESIGN 5.4), from Lua and C alike. It is a native plugin. It draws shapes, lines, textures and text, with the functions draw has for pixels, and vertex buffers with a plugin's own shaders, through pipelines. It holds no scene: the plugin that draws keeps its buffers and says what to draw each frame.
- It uses OpenECS's GPU device, which `ECSGpu_GetDevice` gives (OpenECS DESIGN 9.8): shapes go through an offscreen SDL renderer of its own on the device, `SDL_CreateGPURenderer(device, nullptr)`, and pipelines through SDL's GPU API. Without a GPU device it still loads: its functions that make objects fail, and those that draw log why they cannot.
- **Surfaces.** A GPU panel's `draw` passes its surface to gpu's functions, as it would to draw's. The first call for a surface starts drawing into it, and gpu asks the core to tell it when the `draw` returns (`ECSSurface_OnDrawn`, OpenECS DESIGN 5.4): then it sends what it drew to the GPU, before the core's renderer shows the texture. The plugin that draws makes no call of its own.
- What a `draw` draws keeps its order, shapes and pipelines mixed: draws with pipelines run in one render pass until a shape comes, and shapes go to the GPU before the next pass starts.
- Positions and sizes of shapes are in layout units; gpu multiplies them by the surface's scale. Colours have the type `color` (OpenECS DESIGN 10.2), and gpu blends them by their alpha.
- Its functions for shapes, which take the surface first; those of textures are also methods of the texture in Lua:

  | Function                                                 | Does                                                                                                                                    |
  | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
  | `clear`                                                  | Fill the whole surface with a colour, replacing what it holds.                                                                         |
  | `fill`, `line`                                           | Fill a rectangle, and draw a line in a thickness.                                                                                      |
  | `triangles`                                              | Fill triangles between points, a buffer of x and y floats, with indices, three 32-bit numbers each, or none for points in threes, as draw's do. |
  | `mesh`                                                   | Fill triangles whose points each have a colour, an ARGB 32-bit number, which blends across each triangle. Later triangles cover earlier ones. |
  | `texture`, `updateTexture`, `textureSize`, `freeTexture` | Make a texture of type `gpu.texture` on the GPU from ARGB pixels with premultiplied alpha, as draw's images have; replace its pixels, give its size, and free it. |
  | `image`, `imageTransformed`                              | Draw a texture stretched to a rectangle, or also turned clockwise by an angle in degrees around its centre, with each pixel's colour multiplied by a colour. |
  | `text`                                                   | Draw text in one of draw's fonts at `x, y`, the top left of its line, in a size and a colour, and give its width, as draw's `text` does. |

- A texture keeps its pixels on the GPU, so drawing it each frame costs no upload. `gpu.texture(width, height, image:pixels())` makes one of a draw image.
- **Text.** gpu depends on draw, and takes its fonts: `gpu.text(surface, draw.font("ui"), "Hello", 8, 8, 16, "text")`. `draw.measure` gives the size of such text, at the surface's scale. gpu opens the font's file, which `draw.fontFile` gives, at each size asked for, and keeps it.
- SDL3_ttf's GPU text engine keeps the glyphs in textures on the device, 1024 by 1024 pixels each, and gives the rectangles of a text's glyphs in them. gpu's renderer draws those rectangles, so text keeps its order with shapes.
- `gpu.glyphs(font, text, size)` gives the glyphs of a text for a plugin's own pipeline, such as labels in a 3D scene: its width and its line's height in pixels, and a part for each texture of the text engine that holds some of its glyphs. A part has the texture's `atlas` number, and the glyphs' rectangles as `vertices`, x, y, u and v floats, with x and y in pixels from the line's top left and y going down, and as 32-bit `indices`, six for each glyph. A draw samples the texture by its number. The textures are white, with each glyph's coverage as its alpha, not premultiplied; they keep their numbers while gpu is loaded. Without a GPU renderer, it gives nothing.
- **Pipelines.** A plugin draws with shaders of its own through three kinds of handle, made once and kept:
  - `gpu.buffer(usage, bytes)` makes a buffer of type `gpu.buffer` on the GPU: `"vertex"`, vertices one after another as a pipeline's attributes lay them out, or `"index"`, 32-bit indices. `buffer:update(bytes)` replaces its bytes, `buffer:size()` gives its size, and `buffer:free()` frees it.
  - `gpu.shader(desc)` makes a shader of type `gpu.shader`: `stage`, `"vertex"` or `"fragment"`; its code, as `glsl` source or compiled as `spirv`, `dxil` or `msl`; its `entry` function, `"main"` if missing; and how many uniform blocks and textures it reads, `uniforms` and `samplers`, which gpu counts itself from GLSL or SPIR-V when they are missing. Code that the GPU's driver takes is used as it is. GLSL compiles to SPIR-V, which Vulkan takes; for Direct3D 12, gpu turns SPIR-V into HLSL with SPIRV-Cross, and the HLSL into DXBC with Windows' own compiler, `d3dcompiler_47.dll`. So a plugin ships its shaders in GLSL alone.
  - `gpu.pipeline(desc)` makes a pipeline of type `gpu.pipeline`: its `vertex` and `fragment` shaders; `attributes`, the list of a vertex's attributes at locations from 0, each `"float"`, `"float2"`, `"float3"`, `"float4"` or `"color"`, 4 bytes from 0 to 255; its `primitive`, `"triangles"` if missing; `depth`, whether it tests and writes the frame's depth, true if missing; `cull`, `"none"`, `"front"` or `"back"`, with counter-clockwise front faces; and `blend`, `"none"`, `"alpha"` or `"add"`.
- `gpu.draw(surface, pipeline, draw)` draws `draw.vertices`, a vertex buffer, with a pipeline: through `draw.indices`, an index buffer, if it has one, and `draw.count` of them, or all. `draw.vertexUniforms` and `draw.fragmentUniforms` are each shader's first uniform block, as std140 lays it out, such as from an FFI array of floats, and `draw.texture`, a `gpu.texture`, is the fragment shader's first sampler, sampled linearly; or `draw.atlas`, a texture of glyphs by the number `gpu.glyphs` gave.
- The draws into a surface during one `draw` share one depth texture of its size, `D16_UNORM`, which the first of them clears, so the near primitives of every draw cover the far ones. gpu keeps one for each of the last four sizes it drew.
- Panel textures are `B8G8R8A8_UNORM`, so a pipeline's colour target is too.
- The types of the descriptions are in the plugin's `types.lua`, for editors (OpenECS DESIGN 10.10).
- **Compiling shaders.** gpu compiles GLSL, version 450 for Vulkan, with glslang, the Khronos reference compiler. `gpu.compile(source, stage)` gives the SPIR-V of a vertex or fragment shader, or an empty buffer and why it does not compile, so a plugin can show a shader's errors or keep the SPIR-V. Uniform blocks are in set 1 for vertex shaders and set 3 for fragment shaders, and samplers in set 2, as SDL's GPU API sets them.
- glslang and SPIRV-Cross are C++ libraries, submodules at release tags. std's build builds them with CMake, as shuild compiles only C, into static archives in its cache, for Release in every build type, without glslang's optimizer, its HLSL or its tools. gpu's library takes them, with the C++ compiler's own library, so gpu still needs nothing but OpenECS. They are built once, and again only when the cache is gone. Metal's MSL is not made, as macOS is not worked on (OpenECS DESIGN 19.4).

## 16. cglm

- The `cglm` plugin is the binding of [cglm](https://github.com/recp/cglm), a C library of the math of 3D scenes and shaders: vectors, matrices, quaternions, cameras and noise. It gives cglm to Lua and to C plugins, and cglm itself stays inside it.
- Vectors, quaternions and matrices are struct types (OpenECS DESIGN 10.11): `cglm.vec2`, `cglm.vec3` and `cglm.vec4` have the floats `x`, `y`, `z` and `w` that they need, `cglm.quat` has `x`, `y`, `z` and `w`, and `cglm.mat4` is a list of 16 floats, column by column, as cglm and shaders keep them. In Lua, `v.x` reads a field and `m[13]` a matrix's move along y.
- The functions about a struct are its methods, named as the function without its type: `v:normalize()` is `cglm.vec3Normalize(v)`, `m:inv()` is `cglm.mat4Inv(m)`, and `m:translate(v)` is `cglm.translate(m, v)`. A vector's `add`, `sub` and `scale` are `a + b`, `a - b` and `v * s`, a matrix's `mat4Mul` is `m1 * m2`, and a quaternion's `quatMul` is `p * q`. A vector times a vector is an error, so `dot` and `cross` are methods only.
- A struct is laid out as C lays it out, so it is a buffer itself (OpenECS DESIGN 10.7), and uniforms are matrices and vectors one after another in a `string.buffer`: `vertexUniforms = buffer.new():putcdata(model, 64):putcdata(viewProjection, 64)`.
- A function is named as cglm's, without `glm_` and in camelCase, and takes its parameters in cglm's order; it gives what cglm writes into `dest`. So `glm_mat4_mul(m1, m2, dest)` is `cglm.mat4Mul(m1, m2)`, and cglm's documentation tells what each does:

  | Functions                                                                          | Do                                                                                                   |
  | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
  | `vec2`, `vec3`, `vec4`, `vec2Bytes`, `vec3Bytes`, `vec4Bytes`, `quatBytes`, `mat4Bytes` | Make a vector, and give a struct's floats as bytes. These are the plugin's own.                       |
  | `vec2Add`, `vec2Sub`, `vec2Scale`, `vec2Dot`, `vec2Norm`, `vec2Distance`, `vec2Normalize`, `vec2Lerp`, and the same for `vec3` and `vec4` | cglm's functions of vectors; `vecNNormalize` is cglm's `normalize_to`; `vecNLerp` takes any t.       |
  | `vec3Cross`                                                                         | The cross product.                                                                                   |
  | `mat4Identity`, `mat4Mul`, `mat4Mulv`, `mat4Mulv3`, `mat4Transpose`, `mat4Det`, `mat4Inv` | cglm's functions of matrices; `mat4Transpose` is `transpose_to`.                                     |
  | `translateMake`, `scaleMake`, `rotateMake`, `translate`, `rotate`, `scale`         | The matrices that move, scale and turn; the last three give the matrix they change.                  |
  | `perspective`, `ortho`, `lookat`, `project`                                        | Projections, a camera, and where a point is in a viewport.                                           |
  | `quatIdentity`, `quat`, `quatv`, `quatMul`, `quatNormalize`, `quatSlerp`, `quatMat4`, `quatRotatev` | Quaternions; `quatNormalize` is `normalize_to`.                                                       |
  | `perlinVec2`, `perlinVec3`, `perlinVec4`                                           | Perlin noise at a point.                                                                             |

- The projections give a depth from 0, near, to 1, far, as SDL's GPU API takes it: the plugin and its header define `CGLM_FORCE_DEPTH_ZERO_TO_ONE` before cglm's header. They see down -z, as cglm's do.
- `mat4Inv` gives zeros for a matrix whose determinant is 0, which cglm would invert anyway.
- cglm is a submodule in `dependencies/`, at a release tag. Its functions are inline, in its headers, so the plugin compiles the ones it uses into itself.
- A C plugin calls the plugin's functions through `cglm.h` (OpenECS DESIGN 10.10), which declares the struct types, such as `CglmVec3` and `CglmMat4`: `CglmFunctions_Get(plugin, &cglm)`, then `cglm.mat4Mul(&m1, &m2, &product)`. Neither cglm's headers nor its types reach other plugins.
- The functions copy each struct into cglm's own type, which may need more alignment than the struct has.
- The bytes functions keep their buffer until the next call, as Lua copies it.

## 17. parse

- The `parse` plugin reads common text formats into values, which are Lua tables in Lua, and writes values back into them: JSON, TOML, INI, .env and CSV. It is a native plugin: yyjson reads and writes JSON, and tomlc17 reads TOML; both are compiled into it (1). It writes TOML, and reads and writes INI, .env and CSV, itself, as they are small formats.
- Each format is a namespace (1) with two functions: `parse.json.read(text)` gives the data, and `parse.json.write(data, pretty)` the text; then `toml`, `ini` and `env` with `read(text)` and `write(data)`, and `csv` with `read(text, separator)` and `write(rows, separator)`, whose separator is one character, and a comma when it is empty; another separator is a misuse.
- A function that fails gives nothing and why, as text, with the line where the text is wrong: `local data, problem = parse.json.read(text)`. A text that a write gives, and the reason, are kept until the plugin's next call; Lua gets copies.
- Writes give the same text for the same data: named fields are written sorted by name. A number is written in the shortest form that reads back the same, with a `.` or an exponent, so it reads back as a number and not an integer.
- **JSON:** an object is a table of named fields, an array a list, and `null` is nil, so a field that is null is left out, and a list with nulls has holes. Comments and trailing commas are read. An integer too large for 64 bits is read as a number. A table is written as an array if it is a list, and as an object otherwise, an empty table as `{}`; a table that is both, a handle, or an infinite number cannot be written.
- **TOML:** tables are tables of named fields, and arrays are lists. Dates and times are texts, as TOML writes them, such as `1979-05-27T07:32:00Z`. A table's values are written first, then its tables as `[sections]`, and a list of tables as `[[sections]]`; other tables in lists are written inline.
- **INI:** each `[section]` is a table of its keys, and keys before the first section are fields of the top table. Lines are `key = value`, and lines that start with `;` or `#` are comments. Every value is read as a text, without the quotes around it; a value with blanks at its ends is written in quotes.
- **.env:** `KEY=value` lines, which may start with `export`, give a table of texts. A value in double quotes may span lines and has the escapes `\n`, `\r`, `\t`, `\\`, `\"` and `\$`; one in single quotes is taken as it is; a value without quotes ends at a `#` after a blank. Values are taken as written, without expanding `${...}`. A value with a blank or a character that a shell reads otherwise is written in double quotes.
- **CSV:** a list of rows, each a list of texts, as RFC 4180 says: a field in double quotes holds separators, line breaks and doubled quotes. Rows end with `\n` or `\r\n`. Numbers and booleans are written as texts.
- A text that holds a zero byte is read as a buffer, a string in Lua.
- Lists and tables nest at most 512 deep, in what is read and what is written: deeper data fails, so the plugin's recursion cannot overflow the stack.
- The plugin gives yyjson and tomlc17 SDL's allocator.

## 18. compress

- The `compress` plugin packs and unpacks data, reads and writes zip archives, and makes and reads tar archives. It is a native plugin: zlib packs gzip, zlib and deflate, zstd packs zstd, and zlib's minizip reads and writes zip archives; all are compiled into it (1).
- Each format is a namespace (1): `compress.gzip.pack(data, level)` gives the packed data, and `compress.gzip.unpack(data)` the unpacked data; so do `zlib`, `deflate`, which has no header or checksum, and `zstd`. `compress.unpack(data)` tells gzip, zlib and zstd by the data's first bytes. The level is 1 to 9 for zlib's formats and -7 to 22 for zstd, higher being smaller and slower, and 0 is the format's default. zstd's data may hold many frames.
- `compress.zip.list(path)` lists an archive's entries, each with its `name`, `size` and `packedSize`; a folder's name ends with `/`. `compress.zip.read(path, name)` gives a file of it, unpacked and checked against its checksum. `compress.zip.extract(path, folder)` writes every entry into a folder, and refuses an entry whose name is absolute or goes up with `..`. `compress.zip.write(path, files, level)` writes an archive of a list of files, each a table of its `name` and `data`, packed with deflate, with the current time.
- `compress.tar.pack(files)` gives a tar archive's bytes, in the ustar format that every tar reads, of a list of files, each a table of its `name`, its `data` and whether it is `executable`, with the current time. A name of up to 255 bytes fits, when a slash splits it into ustar's two fields. `compress.tar.unpack(data)` gives the files and folders of an archive, as the same tables; it leaves out links and other kinds of entry. Both pass the archive in memory, so a `.tar.gz` is `compress.gzip.pack(compress.tar.pack(files))`. The plugin writes tar itself, as the format is a header of 512 bytes before each file.
- A function that fails gives nothing, or false, and why: `local data, problem = compress.unpack(packed)`. The reason is kept until the plugin's next call.
- Data passes whole, in memory: a call reads or writes all of it. Paths follow 1.3; minizip reads and writes files through SDL's streams, so paths are UTF-8 on every system.
- The plugin gives zlib and zstd SDL's allocator; minizip allocates with the C library.

## 19. The plugin list

- It shows every plugin in the plugin folders, loaded or not, so the user enables and disables plugins while the tool runs (OpenECS DESIGN 9.10). The first-party Lua plugin `plugins` gives the panel type `plugins.list`, titled "Plugins".
- The core's settings file loads it for every tool (OpenECS DESIGN 12.3). It binds `plugins.open` to `;` after the prefix and adds it to the title bar's menu Tools (OpenECS DESIGN 7.8, 6.8).
- It reads the list with `ecs.plugins.list()` each time it is opened or shown, and again on `ecs.pluginsChanged`. It leaves out itself and the plugins it needs, through others too, as disabling them would close the list. The plugins are sorted by name; each row shows the name, the version, whether the plugin is enabled, disabled or failed, the description, and the plugins it depends on. An enabled plugin that an enabled plugin needs is faded.
- A click on a row, or Return on the chosen one, disables an enabled plugin, unless an enabled plugin needs it (OpenECS DESIGN 9.10), and enables any other, with the plugins it needs.
- A search (5) above the list shows only the plugins whose name, description, version, state or dependencies match it; Up and Down choose among them while it has the keys, and Return enables or disables the chosen one.
- `plugins.open` opens the list, or focuses it if it is open.
- The panel's saved state is the chosen plugin.
- It is built with ui (5), as the panel list is (14).

## 20. process

- The `process` plugin runs programs, for terminals, build tools and linters. It is a native plugin, on SDL's process functions, so it works on Linux and Windows alike. A command is a list of texts: the program, found on the `PATH` unless it is a path, then its arguments. No shell reads it; a plugin that wants a shell runs `sh -c` or `cmd /c` itself.
- `process.start(command, folder, environment)` starts a program in a folder, or in the tool's for an empty one, and gives a handle of type `process.process`, or nothing and why it cannot start. Nothing it does blocks the program, as with net (9): a plugin takes what arrived when it wants, such as from a timer.
- The environment is a list of texts, each `NAME=VALUE`, such as `{ "SDL_VIDEODRIVER=offscreen" }`, set for the program beside the tool's own variables, which a name of the list replaces. An empty list gives it the tool's alone. An entry without `=` is a misuse.
- `process.read(program)` takes what the program wrote to its output since the last read, and `process.readErrors(program)` what it wrote to its errors; each gives an empty buffer if nothing came, and keeps its buffer until its next call on the program. `process.write(program, data)` writes to its input, which must not be closed, and gives false and why if the program cannot take it; what the input's pipe has no room for waits in the handle, and goes at the program's next calls of `write`, `read`, `readErrors` and `exited`, and `process.closeInput(program)` closes it once what waits is sent, for a program that reads to the end of its input.
- `process.exited(program)` tells whether it exited, with its exit code, without waiting. What it wrote before it exited can still be read. `process.kill(program, force)` asks it to stop, or stops it at once.
- These are methods of the handle too: `program:read()`. A program whose handle is gone is killed, so none is left behind.
- `process.run(command, folder, environment, input)` runs a program to its end and gives its output and errors together, with its exit code, or nothing and why it cannot run. The program waits for it, so it suits short programs. The input is written while the output is read, as the input's pipe takes only part of a large input at a time, and closed; then the rest of the output is read. The buffer is kept until the next run.

## 21. gamepad

- The `gamepad` plugin reads game controllers, for games, emulators and tools driven by a controller. It is a native plugin, on SDL's gamepad functions, which map most controllers to one layout of buttons and axes. It starts SDL's gamepads itself, as the core starts only its video.
- `gamepad.list()` lists the gamepads that are plugged in, each with its `id`, `name` and `type`, such as `"xbox360"` or `"ps5"`. `gamepad.open(id)` gives a handle of type `gamepad.gamepad`, or nothing and why it cannot open.
- `gamepad.button(pad, name)` tells whether a button is down, and `gamepad.axis(pad, name)` where a stick or a trigger is: -1 to 1 for a stick, with y growing down, and 0 to 1 for a trigger. Buttons and axes have SDL's names, such as `a`, `start`, `dpup`, `leftx` and `righttrigger`; another name is a misuse. `gamepad.rumble(pad, low, high, seconds)` rumbles its two motors. `gamepad.name(pad)`, `gamepad.id(pad)` and `gamepad.connected(pad)` tell the rest. These are methods of the handle too: `pad:button("a")`.
- The plugin emits `gamepad.added` and `gamepad.removed` when a gamepad is plugged in or out, `gamepad.button` when a button goes down or up, and `gamepad.axis` when an axis moves; each value holds the gamepad's `id` and what changed. A plugin reads a gamepad when it wants, such as each frame of a game, or takes these events, so nothing polls. SDL reads the devices in the core's main loop, and the plugin turns SDL's events into its own there, with an event watch. As games want, SDL ignores the gamepads while none of the tool's windows has the keyboard's focus; the setting `gamepad.background` reads them then too.
- `gamepad.attachVirtual(name)` plugs in a virtual gamepad, of type `gamepad.virtual`, whose buttons and axes the plugin sets with `virtualPress(pad, button, down)` and `virtualMove(pad, axis, value)`; it shows as any gamepad does, with its events. It serves tests, and tools that turn other input into a gamepad's. SDL reads a virtual gamepad at once after each change, so each change gives its event. A virtual gamepad whose handle is gone is unplugged.

## 22. hash

- The `hash` plugin gives checksums and hashes of data, for checking downloads and files, caches and content addresses. It is a native plugin: mbedTLS gives MD5, SHA-1, SHA-256 and SHA-512, zlib CRC-32, and xxHash its fast hashes XXH64, XXH3 and XXH128; all are compiled into it (1).
- `hash.of(algorithm, data)` hashes data that is all in memory. The algorithm is `crc32`, `md5`, `sha1`, `sha256`, `sha512`, `xxh64`, `xxh3` or `xxh128`.
- `hash.new(algorithm)` gives a hasher, a handle of type `hash.hasher`, which takes the data in parts, such as a large file's: `hasher:update(data)` adds a part, and `hasher:digest()` ends the hash and gives it. A hasher that gave its digest takes no more data.
- A hash is hexadecimal text in lower case, as tools such as `sha256sum` and `xxhsum` write it: a number, as CRC-32 and xxHash give, is written with its highest byte first. An unknown algorithm is a misuse, and a hasher that cannot be made gives nothing and why.

## 23. sqlite

- The `sqlite` plugin keeps SQLite databases, for tools that keep many records, such as notes, logs, caches and catalogues. It is a native plugin: SQLite is compiled into it (1), with full-text search and the math functions, and without loading extensions from libraries.
- `sqlite.open(path)` opens a database file, and creates it if it is missing, and gives a handle of type `sqlite.database`, or nothing and why it cannot open. The path follows 1.3; `":memory:"` is a database in memory, which is gone once it closes. A database whose handle is gone closes, and `sqlite.close(database)` closes it at once.
- `sqlite.exec(database, sql)` runs statements separated by semicolons that give no rows, such as `CREATE TABLE`. `sqlite.query(database, sql, parameters)` runs one statement and gives its rows, a list of tables of the columns by name, empty for a statement without rows. The parameters are a list for `?`, or a table of named fields for `:name`, `@name` and `$name`, so a value never becomes part of the SQL. `sqlite.changes(database)` gives how many rows the last change changed, and `sqlite.lastId(database)` the rowid of the last row an `INSERT` added. These are methods of the handle too: `database:query(sql, parameters)`.
- SQLite's integers are integers, its reals numbers, its texts texts and its blobs buffers. A NULL is nil, so a row leaves its field out, and a nil parameter is NULL; a bool parameter is 0 or 1.
- A function that fails gives nothing, or false, and why, with SQLite's message. A database that another program writes makes a call wait up to five seconds before it fails.
- Each call runs to its end on the main thread, so a tool keeps its queries short; many changes are fast inside one transaction, `BEGIN` to `COMMIT`.
- The plugin gives SQLite SDL's allocator.

## 24. notify

- The `notify` plugin shows desktop notifications and tray icons, which OpenECS gives to plugins (OpenECS DESIGN 18). It is a native plugin, on SDL's notification and tray functions: notifications go through the desktop's notification service on Linux and toasts on Windows, and tray icons through the desktop's tray.
- `notify.send(notification)` shows a notification and gives its id, or nothing and why. The notification is a table: its `title`, and optionally its `message`, an `image` file, a `priority` (`low`, `normal`, `high` or `critical`), `buttons`, each with an `id` and a `label`, the id of one it `replaces`, and `transient`, which leaves it out of the system's list once it is gone. `notify.remove(id)` takes it away. The system decides how and whether the user sees it, such as in a do-not-disturb mode.
- `notify.tray(tray)` shows a tray icon and gives a handle of type `notify.tray`, or nothing and why, such as on a desktop without a tray. The tray is a table: its `name`, and optionally its `icon` file, its `tooltip` and its menu `entries`, each with an `id` and a `label`; an entry with `checked` is a checkbox, one with `disabled` is greyed, and one without a label is a separator. `tray:setEntries(entries)`, `tray:setTooltip(text)` and `tray:setIcon(path)` change it. The icon stays until its handle is gone.
- What the user clicks comes back as the plugin's events: `notify.action` with the notification's `id` and the button's id as `action`, or `"default"` for the notification itself; `notify.trayEntry` with the tray's name as `tray`, the entry's id as `entry`, and `checked` for a checkbox; and `notify.trayClicked` for a left click on the icon, as the menu opens with a right click. An event watch turns SDL's events into these; on Windows a notification's click comes on a thread of the system's, so it reaches the main thread with `ECS_RunOnMainThread`.
- Image paths follow 1.3; SDL reads PNG, JPG and BMP files.

## 25. regex

- The `regex` plugin matches regular expressions in UTF-8 text, for searching and filtering, such as a log's lines. It is a native plugin: PCRE2 is compiled into it (1), for 8-bit text with Unicode and without its JIT, with SDL's allocator.
- `regex.compile(pattern, options)` reads a pattern in Perl's syntax once, and gives a handle of type `regex.pattern`, or nothing and why, with the byte where it went wrong. The options are letters: `i` ignores case, `m` makes `^` and `$` match at each line, `s` makes `.` match a newline, and `x` ignores spaces and `#` comments. Text that is not valid UTF-8 can still be searched; a match never starts inside a character.
- `regex.escape(text)` gives a pattern that matches a text exactly, such as what the user typed in a search field.
- The other functions take the pattern first, and are methods of the handle too: `pattern:test(text)` tells whether it matches anywhere, the fastest way to filter; `pattern:match(text, start)` gives the first match from a byte; `pattern:matchAll(text)` every match, each after the last; `pattern:replace(text, replacement)` replaces every match, and `pattern:replaceFirst` the first, giving the new text and how many it replaced; and `pattern:split(text)` the parts between the matches.
- A match is a table: `start` and `stop`, the bytes of the match from 1, as Lua's `string.find` gives them; `text`; `groups`, each group's text in order, or false for a group that matched nothing; and `named`, the texts of named groups, `(?<name>...)`, by name. In a replacement, `$1` or `${name}` is a group's text, and `$$` a dollar.
- After an empty match, the next one must not be empty at the same place, or it starts a character later, as in Perl, so `matchAll` and `split` always end.
- A function that fails gives nothing and why, such as a pattern that reached PCRE2's limit of steps.

## 26. markdown

- The `markdown` plugin reads Markdown as GitHub writes it, with tables, struck text, task lists and bare links, for notes and help panels. It is a native plugin: md4c is compiled into it (1).
- `markdown.parse(text)` gives the document as a tree: each node is a table with its `type` and, for a node that holds others, its `children`. Blocks are `heading` with its `level`, `paragraph`, `quote`, `list` with `ordered`, `start` and `tight`, `item` with `checked` for a task, `codeBlock` with its `language` and `text`, `html` with its `text`, `rule`, `table`, `row` with `head`, and `cell` with its `align`. Parts of a line are `text` and `code` with their `text`, `emphasis`, `strong`, `strike`, `link` and `image` with their `url` and `title`, and `break`. Entities such as `&amp;` become their characters.
- `markdown.elements(text)` gives a description of ui's elements (5), which `ui.showDescription` shows: a column of wrapped texts for paragraphs and headings, larger by level; rows of a mark and the item's blocks for lists; a dimmed, indented column for a quote; the mono font on the colour of fields for code; rows of equal cells for a table, under a head on the colour of the tab row; and a separator for a rule. A paragraph is a text of spans, so emphasis, struck text, code and links keep their style; a heading's spans are larger. A panel puts the description in a scroll element, to scroll what does not fit, and takes the clicked links with `ui.take(panel, "", "onLink")`.

## 27. syntax

- The `syntax` plugin highlights source code with tree-sitter, for code editors and viewers. It is a native plugin: tree-sitter and its grammars of C, Lua and JSON are compiled into it (1), with SDL's allocator. The grammars' highlight queries, `queries/<language>/highlights.scm`, are copied from their repositories into its folder, and read the first time a language is used.
- `syntax.languages()` gives the languages, and `syntax.languageOf(path)` the language of a file by its extension, or nothing.
- `syntax.highlight(language, text)` parses a text and gives its highlighted ranges, in order: each a table of `start` and `stop`, its first and last byte from 1, and its `kind`: `keyword`, `string`, `comment`, `number`, `function`, `type`, `constant` or `punctuation`. Text of no kind is in no range. The first capture of the query that covers a byte names its kind; the query's names map to the kinds by their first word, such as `keyword.function` and `repeat` to `keyword`.
- `syntax.spans(language, text)` gives a list for each line of the text, of ui's spans (5), each a run of one kind in its colour, for `ui.text` in the mono font.
- The colours are settings, `syntax.colorKeyword` to `syntax.colorPunctuation`, whose defaults read on dark and light backgrounds; a theme or the user's settings file may set them.
- A query's predicates `eq?`, `any-of?` and `match?`, and their `not-` forms, are checked. `match?` reads the few regular expressions that the queries use: `^` and `$`, `.`, classes such as `[A-Z\d_]`, the escapes `\d`, `\w` and `\s`, and the quantifiers `*`, `+` and `?`. Directives, which end in `!`, are left out.
- A function that fails gives nothing and why, such as for a language it does not know. Each call parses the whole text.

## 28. video

- The `video` plugin plays video files, for intros, tutorials and previews in a tool. It is a native plugin: pl_mpeg is compiled into it (1), with SDL's allocator. It reads MPEG-1 video, with MP2 sound or none, in an MPEG program stream, such as a `.mpg` file that `ffmpeg -c:v mpeg1video -c:a mp2 -f mpeg` writes.
- `video.open(path)` opens a file and gives a handle of type `video.video`, paused at its start with its first frame, or nothing and why. The path follows 1.3.
- The other functions take the video first, and are methods of the handle too: `play` and `pause`, `playing`, `seek(seconds)`, `time`, `duration`, `size`, `setLoop(loop)` and `setVolume(volume)`. A video at its end stops, unless it loops, and `play` starts it again.
- `video:draw(surface, x, y, width, height)` draws its frame stretched to a rectangle in layout units, with draw (2): video keeps its frame in an image of draw's, whose pixels it replaces with each new frame, and no handle of it reaches Lua. A panel that shows a playing video draws every frame, as a continuous panel does.
- Its sound plays in a stream of mixer's (3), which video fills as it decodes, a little ahead of the frames. A paused video stops its stream, and playing starts a new one.
- A timer decodes the playing videos while there are some, by the time since its last tick.
- `video.free(video)` closes a video at once; its handle is gone otherwise, when no one uses it.

## 29. The files panel

- The first-party Lua plugin `files` shows the files of one folder as a tree, for tools that work on a folder, such as a game's project. It is built with ui (5), fs (10) and process (20), and knows nothing of the tool that uses it.
- The tool names the folder with `files.setFolder(path)`, a path that ends with a slash, or an empty text for none; `files.folder()` gives it. The panel type `files.tree`, titled "Files", shows what is in it, apart from what starts with a dot. fs watches the folder and the folders in it, so the tree follows changes made outside the tool.
- The panel shows the folder as a tree, or one folder at a time as a grid, as a file manager does; a selector above it chooses, and a panel's saved state keeps which, with the folder that its grid shows.
- A search (5) beside the selector shows only the files and folders whose name matches it: in the tree, with the folders above them, open; in the grid, every one under the shown folder, as tiles whose tooltip is the path.
- The grid shows the folder's path as a row of folders, each a button that shows it, and a tile for each of its folders and files, in rows that wrap: an icon over its name, which wraps at the tile's width onto two lines at most, the second ending with an ellipsis when the name is longer; the tile's tooltip is the whole path. An image's icon is a small picture of it; another file's is a badge of its ending, in the colour of the panel's frame, and a folder's a badge in the accent, unless the tool gives its own.
- A click on a file chooses it, and a double click, a second click within 0.4 seconds, opens it. A click on a folder opens or closes it in the tree, and shows it in the grid. `files.selected(panel)` gives a panel's chosen file, by its path in the folder.
- A right click opens a menu (5): on a file or folder, which it chooses, New for a folder, each kind that the tool gives and an empty file, then Open, Show in File Manager, Rename and Delete; beside the files, the New entries only. New makes the file in the chosen folder, or the chosen file's, or beside the files in the shown folder. New and Rename show a field for the name above the tree, which has the keys: Return makes the file or renames it, and Cancel closes the field. A name with folders moves the file. Delete asks first.
- Show in File Manager opens the system's file manager with the file chosen: on Linux through the file manager's D-Bus interface, `org.freedesktop.FileManager1`, and with `xdg-open` on the folder that holds it when no file manager answers; on Windows with Explorer's `/select`.
- The tool says what it adds with `files.setHandlers(handlers)`, a table whose fields may each be left out:

  | Field        | Is                                                                                                   |
  | ------------ | ---------------------------------------------------------------------------------------------------- |
  | `open`       | Opens a file at a double click, by its path in the folder. Without it, a file does not open.         |
  | `choose`     | Shows a file that a click, Up or Down chose, by its path in the folder, such as in a preview.        |
  | `kinds`      | Kinds of file that New makes, each with its `label` and `make(path)`, which makes it and gives whether it did and why not. |
  | `rename`     | Renames or moves a file in place of the panel, such as to change what names it.                     |
  | `delete`     | Deletes a file in place of the panel, such as into the system's trash.                               |
  | `deleteNote` | Gives a text that the question before a delete adds, such as the files that name the file.           |
  | `icon`       | Gives a file's icon in the grid: `{ image }`, an image by its path in the folder, or `{ label, color }`, a badge; nil for the panel's own. |

- A file dragged out of the tree is a drag of type `file-list` with its path, as another application's files come (OpenECS DESIGN 7.9), so a panel that takes dropped files takes it too.
- The panel takes drops of `file-list` (OpenECS DESIGN 7.9): files from another application, and those that a files panel drags. They go into the folder under the pointer: a folder of the tree when they land on its middle, or its tile in the grid; otherwise the folder of the entry they land on, or, beside the entries, the folder's top in the tree and the shown folder in the grid. A file of the folder moves there, through the tool's `rename` when it gives one, as Rename does, and a move into itself or to where it is does nothing. A file or a folder from elsewhere is copied there, with all in it, under its name, or with a number before its ending when the name is taken, `apple 2.png`. The last one is chosen, and the panel emits `files.changed`.
- After a change that the panel makes, it emits `files.changed`.
- `files.reveal(path)` shows a file in each files panel that is not locked, as Unity's Project window follows what is chosen: it chooses the file, without the tool's `choose`, opens the folders above it in the tree, shows its folder in the grid, clears a search that hides it, and scrolls to it. The tool calls it when it shows a file elsewhere, such as an open document.
- The Lock toggle, between the selector and the search, keeps a panel where it is: `files.reveal` passes it by. `files.lock(panel)` turns a panel's lock on or off, for a key.
- A panel's saved state is the folders it has open in the tree, whether it shows the grid, the grid's folder, its lock and its chosen file.

## 30. The viewer

- The first-party Lua plugin `viewer` shows a file as what it is, with the standard loaders: an image with image (6), shown through ui (5), a sound with audio (7), which mixer (3) plays, and a text with syntax (27). It knows nothing of the tool that uses it.
- `viewer.open(path)` shows a file in the panel that shows it, or in the first panel of type `viewer.file` that is open, or in a new one; the panel gets the focus. `viewer.show(path)` shows a file as a preview: in the panel that shows it, or in the first one open, without the focus; with no panel open, it does nothing. `viewer.reload(path)` reads the file again in the panels that show it.
- An image fills the panel: a large one whole, and a small one by a whole number of times, at most 16. A sound has Play and Stop, and its length.
- A text shows in the mono font, coloured by syntax when syntax knows its language, its first 2000 lines of at most its first MiB. A line wider than the panel wraps, and each row after its first starts with a dim `↪`, ui's `wrapMark`; the file's path above it wraps too. A file with a zero byte is not text. Of any other file, the panel shows its size.
- A panel's saved state is the file's path.

## 31. The console

- The first-party Lua plugin `console` is a log that other plugins add entries to, such as what a program they run prints. It is built with ui (5), and knows nothing of the tool that uses it. Its panel type is `console.log`, titled "Console".
- `console.add(text, level, links, source)` adds an entry: a text, which may hold many lines, with its level, `info`, `warn` or `error`, and its source, where it comes from, such as `game` for what a tool's game prints; an empty source is `output`. An entry shows as a box framed in its level's colour, the theme's `warning` or `error` (OpenECS DESIGN 12.4), with the time it was added, its source, the first file and line it names, and its text. An entry equal to the last one, in text, level and source, stacks on it: its count shows, and its time is the last one's. The console keeps the last 2000 entries. `console.clear()` empties it, as its Clear button does, and `console.entries()` gives the entries (`console.Entry`).
- The console takes in every line of the log (OpenECS DESIGN 14.4), from the core's event `ecs.logged`, as the core's setting `ecs.log` chooses them. Each line's source is its plugin's name, `ecs` for the core's, and its time is the line's. An entry's level is `debug`, `info`, `warn` or `error`.
- A bar above the entries holds a search (5), which shows only the entries whose text matches it, the Show dropdown and Clear. Show shows the entries from a level up: Errors, Warnings and up, Info and up, or Everything, which adds debug; each choice says how many entries it shows, and a change shows at once. A new console starts from the setting `console.show`, a `choice` of these four names, whose default is Warnings and up; a tool whose users' prints are info, such as a game's, sets Info and up in its preset. A change of Show changes only its panel, not the setting. Below the bar, a checkbox for each source, in the order of their first entries, shows how many entries it has and hides them or shows them again, so one console shows a tool's game apart from the editor's warnings. A panel's saved state is the level it shows from and the sources it hides, so two consoles filter apart, and a console restored from a session keeps its own level, whatever the setting says.
- The console knows nothing of runs: a tool that wants an empty console for each run of its program calls `console.clear()`, and gives its user the choice in its own settings.
- The first file and line that an entry names, such as `src/main.lua:12`, is a link. A click on it, or `console.open(file, line)`, opens the file at the line in the user's code editor, with the command of the setting `console.editor`, in which `{file}` and `{line}` stand for them. A relative path starts at the folder that `console.setFolder(path)` names.
- From Lua, `console.add(text, level, links)` may give an entry more links, shown after its place: each a table of its text, a tooltip and `onClick`, the function that a click calls (`console.Link`). A tool links an error to what it came from this way, such as the object that raised it. An entry that stacks takes the last links.
- The command's words are split at spaces, and a word in double quotes keeps its spaces, such as `"C:\Program Files\Editor\editor.exe" {file}`. The console finds its program as a path or in the folders of `PATH`; on Windows it tries each ending of `PATHEXT` too, so `code` finds `code.cmd`, which Windows starts through cmd. It starts the command with process (20). When the program is not there, or does not start, the system opens the file with the program that it has for such files, and the console warns once.
- The entries are a list. A click on an entry chooses it, and a second click on it within 0.4 seconds, a double click, goes to what it is about: the file and line that it names, or else its first link. A right click opens its menu, of Go to and Copy. Ctrl+C, bound to `console.copy`, copies the chosen entry's text, with its count when it stacked.
- The panel follows its last entry as entries are added.

## 32. The profiler

- The first-party Lua plugin `profiler` shows where the main thread's time goes, as the core measures it while the setting `ecs.profile` is on (OpenECS DESIGN 3.5). Its panel type is `profiler.view`, titled "Profiler". It is built with ui (5).
- The core's settings file loads it for every tool (OpenECS DESIGN 12.3). It binds `profiler.open` to `F` after the prefix and adds it to the title bar's menu Tools (OpenECS DESIGN 7.8, 6.8). `profiler.open` opens the panel, or focuses it if it is open.
- Its Measure switch turns `ecs.profile` on and off with `ecs.setting.set`. While it is off, the panel says how to turn it on.
- The panel reads `ecs.profile.get()` every half second, not in each draw, so its own drawing stays small. Its Pause toggle keeps the numbers that show, to read or copy them.
- A line sums up the last passes that drew a frame: how many, and their average and longest time without the wait.
- A graph (5) shows each of the last passes without its wait, the oldest on the left, in four stacked parts: input, timers and events; layout; panels with their uploads; and the interface with present. A line marks a frame at 60 Hz, and a line of text names the parts in their colours.
- Tabs choose a table: Plugins, each plugin's own time in the last second, as a share of the second and in milliseconds, its longest call and its calls; Panels, each panel's draw the same way, named by its title and type; Functions, the Lua functions that took the most of the last second, by LuaJIT's sampling profiler, each with its plugin, share of the second, milliseconds and samples; Steps, each step's average and longest time over the last passes.
- Copy report puts the whole profile on the clipboard as text, so a user can send where the time goes.

## 33. The key list

- The first-party Lua plugin `keys` shows every key binding of the tool, and changes them in the user's settings, with `ecs.key.list`, `ecs.key.set` and `ecs.key.functions` (OpenECS DESIGN 7.8). Its panel type is `keys.list`, titled "Keys". It is built with ui (5).
- The core's settings file loads it for every tool (OpenECS DESIGN 12.3). It binds `keys.open` to `K` after the prefix and adds it to the title bar's menu Tools (OpenECS DESIGN 7.8, 6.8). `keys.open` opens the list, or focuses it if it is open.
- The bindings that run show in a section for each scope: Everywhere, for the whole tool; After the prefix; then each panel type, by its title. A row shows the function's description and name, and its key as a key element (5): a click on it, then a key press, gives the function that key instead. A binding that removes a key shows as Removed.
- A new key binds the function in the user's settings, and the old key is taken away: the user's own binding goes with nil, and a key that a layer below still binds to the function is removed with false. Remove takes a key away the same way. A row that the user's settings give shows its title in the accent, and a Reset button, which takes the user's binding away, so the preset's or the default applies again.
- Add a key, above the sections, binds a key for a function, chosen in a dropdown of every function that a key can run, in folders by their names' dots, in a scope chosen in another.
- A search (5) shows only the rows whose key, function, description or scope matches it, with their sections open.
- The list reads the bindings again when it is shown, on `ecs.pluginsChanged`, when `ecs.prefix` changes, and after each change it makes. The panel's saved state is the scopes whose sections are closed.
- The plugin also shows the keys after the prefix while the core waits for one, from the core's event `ecs.prefix` (OpenECS DESIGN 7.5, 8.4): a popup of type tooltip at the bottom right of the focused panel's OS window, a margin from its edges, placed from `panel.place` (OpenECS DESIGN 4.6) and drawn with draw (2), which closes when the core waits no more. It lists each key and what it does now, in sections: Navigation (focus, move, tabs and workspaces), Panel (the core's other functions on the focused panel), Layout (closing a group, locking it and resetting the layout), Session (saving and opening sessions, the title bar's menus and quitting) and More (the plugins' functions). A section without keys has no heading, and Escape, Cancel ends the list.
- Keys of one kind share a line. The keys that switch workspaces show the first workspace's key to the last one's: `1...0`, and the keys that move the focused panel to a workspace the same way: `Shift+1...0`. Focus and move show `Arrows` and `Shift+Arrows` when their four functions are on the four arrows with the same modifiers.

## Glossary

**Archive (static).** A file that holds compiled code, which a library or a program takes in when it is linked.

**Certificate.** A file with which a server proves who it is to HTTPS. It is trusted when an authority that the system trusts signed it.

**Datagram.** A message sent by UDP on its own, without a connection.

**D-Bus.** The way programs of a Linux desktop call each other, such as to ask the file manager to show a file.

**Ellipsis.** The three dots, …, that end a text that is cut.

**PEM.** A text file that holds certificates or keys in base64, between lines such as `-----BEGIN CERTIFICATE-----`.

**Proxy.** A server that makes requests for other programs.

**Rasterizer.** Code that turns a shape into the pixels it covers.

**Redirect.** An answer that tells the client to ask another URL instead.

**Thumb (scrollbar).** The part of a scrollbar that shows which part of the content is in view, and that the user drags to scroll.

**TLS (Transport Layer Security).** The protocol that encrypts HTTPS and other connections, and checks the server's certificate.
